## Context

Design System 目前有五個元件重造了系統既有能力。它們的共通模式是：為了取得特定外觀而從底層零件重新拼裝，過程中沒有把系統元件原本附帶的行為一併重建。這些行為多半不可見——progress 語意、Search return 鍵、列的按壓回饋——因此缺失不會在目視檢查中暴露。

其中三個元件在 repo 內零呼叫點，只存在於 Design System 目錄中等待被採用。它們的存在本身就是問題：Design System 的預設語意是「這裡的元件是本專案的標準作法」，一個有缺陷的元件放在那裡等同於背書。

另有三處自訂控制項缺少互動回饋。與前者不同，這些不需要換成系統元件，只需要補上系統元件本會提供的狀態表達。

現有約束：搜尋欄的兩個呼叫點都在導覽堆疊內，系統搜尋呈現可直接套用；版面變動會使 snapshot baseline 失效。

訂單列表經評估後決定維持自製分組結構，理由見 Non-Goals。但查證時發現承載日期區段的容器並非惰性容器，因此所有訂單列在呈現時一次全數建構——這項成本原本被歸因於「沒有系統清單的 cell 回收」，實際上與是否採用系統清單無關，可獨立解決。

## Goals / Non-Goals

**Goals:**

- 讓「系統已提供的能力不得重造」成為可被檢查的契約，而非口頭慣例。
- 移除零呼叫點的重造元件，使 Design System 目錄內不再有等待被誤用的規範債。
- 取回被自製版本丟失的系統行為：progress 語意、搜尋列的完整行為、列的按壓回饋。
- 讓自訂控制項的停用態、按壓態與破壞性語意由系統機制表達，而非各自以視覺樣式模擬。
- 讓刻意保留的自製結構承擔其對應責任，不因「不採用系統元件」而順帶放棄可獨立解決的能力。

**Non-Goals:**

- 不處理 blocker 與 suggestion 等級的發現。
- 不刪除非重造類的零呼叫點元件。
- 不改用系統清單重寫訂單列表。該改動會同時重寫呈現與多選狀態機，且無法在維持既有卡片外觀的前提下完成；維持自製結構意味著訂單列表繼續沒有 swipe actions 與分隔線自動對齊，此為知情的取捨。列回收不在此取捨之列，見下方決策。
- 不改動圖表元件的實作方式。
- 不擴充搜尋的資訊架構到目前沒有搜尋的畫面。
- 不調整未被點名重造的既有元件。

## Decisions

### 搜尋欄改用系統搜尋呈現並刪除自製元件

自製搜尋欄失去的行為清單很長：Cancel 鈕、Search return 鍵、聽寫、捲動時的收合與展開、以及搜尋範圍。這些不是可以逐項補回的細節，而是系統搜尋呈現作為一個整體提供的體驗。逐項模擬的成本遠高於直接採用，且永遠追不上系統的後續演進。

兩個呼叫點都位於導覽堆疊內，系統搜尋呈現可直接套用。專案內已有四處正確使用系統搜尋呈現的範例可對照。

刪除元件而非保留：留著它就會再被採用。前一個 change 已將其命中區缺口記錄為「由本 change 以取代方式解除」，因此本 change 必須確實刪除而非修補。

### 進度條改用系統進度視圖並保留既有版面

自製進度條缺少 progress 無障礙語意，輔助技術讀到的是兩段散落文字而非「進度百分比」。系統進度視圖原生提供該語意，同時支援樣式與著色的系統慣例。

既有的「標題在左、數值在右、進度條在下」版面可由系統進度視圖的標籤與當前值標籤表達，字型差異以修飾子疊加即可，不需要保留自繪結構。六個呼叫點的視覺結果應與變更前一致。

### 設定頁 disclosure row 改用系統元件

手繪的列失去了列的按壓 highlight，因此看起來與按起來都不像可點擊，且自畫的指示符號與系統的 disclosure indicator 不一致。改用系統元件同時解決兩者。

### 分段控制元件直接刪除

該元件零呼叫點，而專案內已有兩處正確使用系統分段選擇器。保留它沒有任何收益，刪除是純減法。

### 維持自製分組結構，但以惰性容器承擔列回收責任

改用系統清單無法在維持既有卡片外觀的前提下完成：卡片的 16pt 連續圓角、0.5pt 描邊與淺色模式陰影，在系統清單中分別無法指定半徑、沒有對應 API、以及會被列邊界裁切。逐列以列背景重繪這三者，等同用系統清單重新手繪卡片，比現行結構更複雜且更脆弱。因此維持自製結構。

但「不採用系統清單」不等於可以放棄列回收。承載日期區段的容器目前非惰性，所有區段在呈現時一次全數建構，這與是否採用系統清單無關，改為惰性容器即可解決。

惰性化只施加於外層的日期區段容器。單一日期區段內的訂單列容器必須維持非惰性——卡片的背景、圓角與描邊需要在佈局時得知完整內容高度，而惰性容器的高度是隨捲動漸進確定的，會使卡片背景無法完整包住其所有列。單一日期的訂單數本就有限，該層非惰性不構成成本問題。

### 自訂按鈕樣式讀取啟用狀態

按鈕樣式自繪背景卻不讀取環境中的啟用狀態，導致停用的按鈕外觀與可用時完全相同。使用者按下去沒反應卻沒有任何線索。修法是讀取啟用狀態並在停用時降低不透明度，與系統按鈕樣式的表現一致。

### 破壞性動作改以按鈕角色表達

目前把破壞性做成一種視覺樣式變體。角色才是系統語意來源——它決定語音播報、系統紅色在各外觀下的自動調整、以及在確認對話框與選單中的一致呈現。改為在呼叫端標註角色，樣式端不再提供破壞性變體。

### 照片縮圖的點擊改用按鈕

目前以點擊手勢觸發並補上按鈕特徵標記，但點擊手勢沒有按壓態，也不支援輔助操作與鍵盤啟用路徑，與真正的按鈕語意不等價。改用按鈕即可同時取得三者。

## Implementation Contract

#### 行為

- 訂單列表與其他搜尋入口顯示系統搜尋列，具備 Cancel 鈕、Search return 鍵、聽寫與捲動時的收合展開；輸入文字後可一鍵清除，且清除控制項的命中區符合系統標準。自製搜尋欄不再存在於程式碼中。
- 開啟 VoiceOver 聚焦任一進度條時，播報內容包含該進度的當前值而非僅有兩段文字。
- 設定頁的可點擊列在按下時有 highlight，並顯示系統的 disclosure indicator。
- 訂單列表在資料量增長時，呈現成本不隨訂單筆數線性增長；捲動至列表深處時，各日期區段的卡片圓角、描邊與背景仍完整包住當日所有列。
- 停用的按鈕具備與可用態可辨識的視覺差異。
- 破壞性按鈕由系統呈現為破壞性語意，包含顏色與語音播報。
- 照片縮圖在按下時有視覺回饋，並可由輔助操作與鍵盤啟用。

#### 介面與資料形狀

- 自製搜尋欄與分段控制元件的原始檔自 Design System 目錄移除，其型別不再存在。
- 進度條元件對外的呼叫形狀維持不變（標題、數值、選用的著色），內部改以系統進度視圖實作。
- 訂單列表承載日期區段的容器改為惰性垂直容器；單一日期區段內的訂單列容器維持非惰性。
- 按鈕樣式不再提供破壞性變體；破壞性語意由呼叫端以按鈕角色表達。

#### 失敗模式

- 系統搜尋呈現與自製版本的觸發時機不同：自製版本每次輸入即過濾，系統版本亦然，但取消搜尋時系統會清空文字。功能狀態需正確處理清空事件，避免停留在已過濾狀態。
- 進度值超出範圍時，系統進度視圖會自行截斷；既有的範圍限制邏輯需保留以免顯示與資料不一致。
- 若惰性化誤施於卡片內的訂單列容器，卡片背景會因高度漸進確定而無法完整包住所有列，出現背景缺口或圓角錯位。

#### 驗收標準

- 全專案搜尋不到已刪除的兩個元件型別，且 iOS 與 iPadOS 皆建置成功。
- 實機以 VoiceOver 聚焦進度條，確認播報包含進度值。
- 實機確認設定頁列有按壓回饋、停用按鈕有視覺差異、照片縮圖有按壓態。
- 以數百筆、橫跨多個日期的訂單資料集捲動列表，確認初次呈現時間不隨筆數明顯增長，且捲動至深處時卡片外觀完整。
- 既有單元測試調整後全數通過；受版面變更影響的 snapshot baseline 重錄後差異僅限預期範圍。
- 字串目錄的中英完整性測試通過。

#### 範圍邊界

**在範圍內：** 四個重造元件的取代或刪除 (搜尋欄、分段控制、進度條、設定頁 disclosure row)；訂單列表日期區段的惰性建構；三處自訂控制項的互動回饋補齊；上述變更牽動的呼叫點、功能狀態、字串目錄與 snapshot baseline。

**在範圍外：** 訂單列表改用系統清單 (含隨之而來的 swipe actions 與自動分隔線對齊)；blocker 與 suggestion 等級的發現；非重造類的零呼叫點元件；圖表元件實作方式；搜尋資訊架構的擴充；未被點名重造的既有元件。

## Risks / Trade-offs

- [惰性化若施加層級有誤，會使卡片背景無法完整包住其所有列] → 僅對外層日期區段容器惰性化，卡片內的訂單列容器維持非惰性；驗收時捲動至列表深處逐一確認卡片圓角、描邊與背景完整。
- [刪除搜尋欄元件後，若系統搜尋呈現的過濾時機與自製版本不同，可能改變既有的搜尋體感] → 驗收時對照變更前的過濾行為，特別確認取消搜尋時功能狀態正確重置。
- [破壞性樣式變體移除後，若有呼叫端漏改角色標註，該按鈕會失去紅色而不會編譯失敗] → 移除變體後全專案搜尋原變體名稱確認無殘留，並於實機逐一目視確認破壞性按鈕仍為紅色。
- [六個進度條呼叫點的視覺結果需與變更前一致，但系統進度視圖的預設樣式與自繪版本有差異] → 以 snapshot 差異逐張比對，確認變化僅來自系統樣式的細微差別而非版面錯位。
