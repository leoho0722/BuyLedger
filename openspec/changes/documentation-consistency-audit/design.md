## Context

專案的文件同步鐵則要求每完成一項開發就對照變更檢視文件，並得出「有影響，已同步」或「確認無文件影響」兩種結論之一。前八個 change 都各自帶有這樣一項任務。

這個機制在單一 change 的尺度上有效，但有三個結構性的盲點。其一，被推翻的既有描述往往落在責任邊界之外：刪除某個機制的 change 會記得改寫該機制的規則，卻不會注意到另一節的排版慣例正好以該機制的檔案為例。其二，每個 change 各自新增規則是合理的局部決定，但沒有任何一個 change 負責累積後的整體結構。其三，稽核時順帶發現的既有漂移若不明確標示來源，會在逐項核對時被誤認為已檢查。

稽核前已定位的失效點集中在平台指引，共五處：收鍵盤的完整硬規則、extension 放置規則的舉例、本地化規則的舉例、Design System 檔名規則的舉例、以及底部工具列規則的結尾。另在說明文件發現既有漂移：專案結構樹漏列兩個既有目錄，相依注入目錄的數量描述與現況不符。

程式碼註解具有完全相同的結構性盲點。專案在每個 change 實作完成後會跑一次註解風格審查，但那只針對該 change 的變更檔；一條註解可能位於未被任何 change 修改的檔案，卻因別處的變更而失效。已確認的三個案例分屬三種失效類型：註解解釋某個設計選擇的理由而該理由已不成立、註解描述的實作意圖與實際程式碼不符且實作決定不改、以及註解記錄的踩雷知識其適用範圍已超出所在檔案。

本 change 對原始碼檔案的變更僅限註解文字，不改動任何可執行語句，因此無 runtime 或行為影響；但因觸及原始碼檔案，仍需建置驗證以確認未意外改壞。

## Goals / Non-Goals

**Goals:**

- 確認前八個 change 宣告的文件更新確實落地，而非僅在任務清單上被勾選。
- 消除文件中與現況矛盾的描述——與現況矛盾的文件比缺文件更糟。
- 讓文件的正確性可被驗證，而非依賴逐句人工判讀。
- 讓八個 change 累積的新增規則維持可讀的層級結構。
- 讓程式碼註解與文件受到同一個「不得與現況矛盾」的標準約束。

**Non-Goals:**

- 不修改任何程式邏輯；對原始碼的變更僅限註解文字。
- 不執行註解的風格合規審查，該職責屬各 change 實作後的專責風格閘門。
- 不直接修改生成檔的註解。
- 不重寫文件的整體架構。
- 不做全文重審；既有漂移的處理限縮於稽核中實際發現者。
- 不建立自動化檢查工具或持續整合檢查。
- 不變更通用規範與平台細節的歸屬原則。

## Decisions

### 以符號存在性作為文件正確性的客觀依據

逐句判讀文件是否與現況相符，成本高且結論主觀。但文件中大量出現具體的型別名、檔名與 API 名，這些是可機械查核的：文件提到某個型別，該型別就應存在於程式碼中。

因此採兩層稽核：先以符號存在性掃描出「提到了不存在的東西」，這類必然是錯誤；再對掃描不到的部分（描述行為與慣例的散文）以前八個 change 的變更清單為索引逐項核對。前者提供客觀底線，後者處理語意層面。

反向的檢查——程式碼中存在但文件未提及——不納入。文件本就不需窮舉所有型別，缺漏不等於錯誤。

### 以各 change 的文件任務宣告作為核對索引

每個 change 的文件同步任務都明確寫出了要寫入哪些規則、要移除哪些失效描述。這些宣告構成一份可逐項核對的清單，比重新閱讀八個 change 的完整 diff 更可靠也更省力。

核對的判準是文件的實際內容，而非任務是否被標記完成——任務被勾選但內容未落地，正是本 change 要抓的情況之一。

### 結構整理限於分層與合併，不刪減規則

八個 change 新增的規則各有其來由，稽核不重新評估其必要性。整理僅限於：語意重疊者合併為一條、細節與 caveat 降為次層級、同主題者相鄰排列。

依專案既有的文件慣例，精簡是減字而非減規則，分層是重排而非刪除。任何實質規則的移除都超出本 change 範圍，應回到對應的 change 討論。

### 註解稽核只問「是否與現況矛盾」，不問風格

專案已有針對註解風格的專責閘門，在每個 change 實作完成後針對該 change 的變更檔執行，涵蓋中文用語、結尾標點、半形括號與空格等規範。本 change 若重複那件事，既浪費也會與該閘門的結論衝突。

因此判準單一：這條註解描述的東西現在還成立嗎。風格問題即使在稽核過程中被看見也不處理，維持職責分工清晰。

反過來說，本 change 補上的正是風格閘門結構上看不到的部分——未被任何 change 修改、卻因別處變更而失效的註解。

### 註解失效分三類，處理方式各異

第一類是註解解釋某個設計選擇的理由，而該理由已不成立。處理方式是連同解釋一併改寫，或在該設計選擇本身已被移除時刪除整段。

第二類是註解描述的實作意圖與實際程式碼不符。此時要先確認哪一邊是對的：若實作應該改，那屬於對應 change 的範圍而非本 change；若實作決定維持現狀 (例如已被明確排除於實作範圍之外)，則應修的是註解，使其反映實際做法而非未竟的意圖。

第三類是註解記錄的踩雷知識其適用範圍已超出所在檔案。這類註解本身仍然正確，處理方式是識別並記錄其是否該提升為文件層級的硬規則，但不在本 change 逕行搬移——搬移涉及規則的措辭與歸屬層級判斷，應作為獨立決定。

### 生成檔的註解只記錄不修改

生成檔由產生器輸出，其註解由產生器在輸出時統一處理，且檔案在磁碟上為唯讀以防手動編輯。直接修改生成檔的註解會在下次重新產生時消失，也會使生成檔與 schema 的同步檢查失敗。

因此掃描涵蓋生成檔但處理不涵蓋：發現的問題記錄為產生器待修項目，由後續改動產生器並重新產生來解決。

### 既有漂移逐項列出來源，不與本次失效混談

稽核中發現的既有漂移與前八個 change 無關。這些在任務中逐項列名，並標明其為既有問題，避免日後回顧時誤以為是某個 change 造成的。

處理與否的判準是修正成本：結構樹補列目錄、數量描述改為不綁定數量，兩者成本皆低且能防止再次漂移，因此納入。需要重新查證才能斷言正誤的描述不納入，改為在稽核筆記中記錄待查。

## Implementation Contract

#### 產出

- 一份稽核筆記，記錄逐項核對結果：每個 change 的文件宣告項及其落地與否、符號存在性掃描的結果、既有漂移的處理決定、失效註解的判別與處理、以及待提升為文件規則與待修產生器的記錄。
- 修正後的平台指引與說明文件，其中不含與現況矛盾的描述。

#### 驗收標準

- 平台指引與說明文件中提及的每一個型別名與檔名，皆可在程式碼中找到對應的宣告；掃描結果為零筆不存在。
- 前八個 change 的文件同步任務所宣告的每一項更新，皆可在文件中指出其落地位置。
- 稽核前已定位的五處失效描述皆已改寫，且改寫後的內容與各該 change 的實際實作一致。
- 說明文件的專案結構樹涵蓋所有既有的原始碼目錄。
- 平台指引新增的規則依主次層級排列，無語意重複的條目。
- 稽核筆記中的每一項既有漂移皆有處理決定 (已修正或記錄待查)。
- 原始碼檔案的變更僅含註解行；以差異比對確認無任何可執行語句被更動。
- iOS 與 iPadOS 皆建置成功，確認註解變更未意外改壞原始碼。
- 三個已確認的失效註解案例皆已依其類型處理，且處理方式與各該 change 的實際實作一致。
- 生成檔的註解未被直接修改；若掃描發現問題，其記錄存在於稽核筆記的產生器待修項目中。

#### 範圍邊界

**在範圍內：** 前八個 change 文件宣告的落地核對；五處已定位失效描述的改寫；符號存在性掃描與其結果的修正；累積規則的分層與合併；稽核中發現且成本低的既有漂移；手寫原始碼中失效註解的判別與改寫；生成檔註解問題的記錄。

**在範圍外：** 任何程式邏輯的變更；註解的風格合規審查；生成檔註解的直接修改；踩雷知識提升為文件規則的實際搬移；文件架構重寫；全文重審；自動化檢查工具；通用與平台細節的歸屬原則。

## Risks / Trade-offs

- [本 change 依賴前八個全部落地，若在其中若干尚未完成時執行，會對照到不完整的現況而做出錯誤修正] → 任務第一組確認八者皆已完成，未完成則不啟動；若因故需提前執行，則僅處理已完成 change 對應的文件項並在稽核筆記中標明未涵蓋範圍。
- [符號存在性掃描會誤報：文件中的示意名稱、已規劃但未實作的名稱、或程式碼註解中的字串] → 掃描結果逐筆人工判定而非機械修正；誤報在稽核筆記中標記為誤報並說明理由，不改動文件。
- [結構整理可能在合併規則時改變其語意] → 合併僅限語意確實重疊者；合併後逐條回讀確認每條原規則的約束力未被削弱，有疑慮者維持分列。
- [註解稽核觸及原始碼檔案，存在誤改可執行語句的風險] → 以差異比對確認變更僅含註解行，並以 iOS 與 iPadOS 建置驗證；此檢查列為驗收標準而非事後補做。
- [註解與實作不符時，可能誤判該修哪一邊而擅自改動實作意圖] → 判準明確：實作應改者屬對應 change 範圍、本 change 不碰；僅在實作已決定維持現狀時才修註解，且需指出該決定的出處。
- [既有漂移的邊界不易界定，容易擴散為全文重審] → 僅處理稽核過程中因前述兩項工作而順帶發現者；主動全文尋找漂移不在範圍內。
