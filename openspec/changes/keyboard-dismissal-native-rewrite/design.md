## Context

收鍵盤目前由單一的 window 級點擊手勢承擔，掛載點在根視圖。因為掛在 window 上，它會收到畫面上每一個觸控，因此必須沿著視圖層級逐層往上判斷這個觸控該不該觸發收鍵盤。判斷分兩類：互動控制項與文字輸入視圖以公開型別檢查，可靠；系統的文字選單、選取控制點與放大鏡則只能以私有型別的類別名稱關鍵字比對。

查證現況可知改寫的實際規模：專案中的焦點狀態實質為零——唯一一處在自製搜尋欄，而該元件將由 design-system-component-reduction 刪除；捲動收鍵盤只有一處且採立即模式；window 手勢只有一個掛載點。有文字輸入的畫面共八個，其中訂單編輯已由 touch-target-and-input 排定導入焦點狀態，另有兩個輸入元件將被刪除。因此本 change 實際需要導入焦點的畫面為七個。

順帶可確認的是，現行黑名單中的兩個文字輸入類別名稱是冗餘的——它們已被前一行的文字輸入協定型別檢查涵蓋，真正依賴私有名稱的只有五個。

前置條件：ui-polish-and-safeguards 已為現行行為建立回歸測試，該測試斷言「選取文字後點擊系統選單，鍵盤不收起」。這個斷言描述的是行為而非實作，因此改寫後應繼續通過——它正是本 change 的安全網。

## Goals / Non-Goals

**Goals:**

- 讓收鍵盤不再依賴任何私有型別名稱比對，使問題從根消失而非變得可觀測。
- 讓每一種鍵盤情境都有明確且可指認的收起路徑，不再有「靠一個全域手勢兜底」的模糊地帶。
- 讓使用者感受到的收鍵盤行為在改寫前後一致。

**Non-Goals:**

- 不移除點空白處收鍵盤這項行為，僅改變實作方式。
- 不重新設計任何畫面的輸入流程或欄位順序。
- 不處理訂單編輯表單的焦點狀態，該項由 touch-target-and-input 涵蓋。
- 不新增鍵盤工具列到原本沒有數字鍵盤的畫面。
- 不改動搜尋列的收鍵盤行為。

## Decisions

### 以背景層點擊取代 window 級攔截，把黑名單換成白名單

window 級攔截必須列舉所有不該收鍵盤的情況，這是黑名單模型，而黑名單無法窮舉未來的系統介面。

改為在畫面的背景層放置一個透明且可命中的區域，點擊它才收鍵盤。系統文字選單、選取控制點與放大鏡都不在該背景層的命中測試範圍內，因此不需要任何排除邏輯。這是白名單模型：只有明確標示為背景的區域會觸發。

背景層採用背景修飾子內的透明填色搭配形狀宣告，而非在畫面最外層直接掛點擊手勢。理由是後者仍會參與整個畫面的命中測試，雖然子視圖會優先取得觸控，但一旦某個子視圖沒有自己的觸控處理，點擊仍會穿透到最外層——這會重新引入「哪些區域算背景」的判斷。放在背景層則從結構上保證只有真正的空白處會響應。

### 收鍵盤以焦點狀態實作，不呼叫 UIKit 的結束編輯

現行實作呼叫 UIKit 的結束編輯方法。改為將焦點狀態設為無，由 SwiftUI 自行收起鍵盤。這使收鍵盤與焦點成為同一個狀態的兩面，避免出現「鍵盤已收起但焦點狀態仍指向某欄位」的不一致。

### 焦點狀態的放置依專案既有慣例分流

專案規範是綁定 store 的視圖不持有呈現狀態，但不綁 store、以閉包與呼叫端溝通的可重用元件的本地狀態屬元件內部狀態，不在此列。

因此：綁定 store 的畫面 (開團編輯、匯率工具、報價試算、設定、主檔管理) 把焦點欄位放進對應的功能狀態，由視圖以綁定連結；不綁 store 的元件 (選項選擇器、付款方式編輯器) 的焦點狀態留在元件本地。這與 touch-target-and-input 為訂單編輯所做的安排一致。

### 共用修飾子以泛型承載各畫面不同的焦點型別

各畫面的焦點欄位型別不同，因此共用修飾子以泛型參數承載焦點綁定，內部只負責建立背景層與清除焦點。修飾子不持有任何狀態，也不假設焦點型別的具體內容。

### 移除整個手勢檔案，而非留下停用的程式碼

手勢的視窗追蹤輔助視圖、手勢代理與私有名稱比對是一組互相依賴的實作，只移除比對而保留其餘沒有意義。整個檔案刪除，其匯出的修飾子一併移除，並在根視圖移除掛載。

### 沿用既有回歸測試作為改寫的驗證基準

ui-polish-and-safeguards 建立的測試斷言的是行為——選取文字後點擊系統選單時鍵盤不收起——與實作無關。改寫後該測試應繼續通過。若改寫後測試失敗，代表新機制在某處仍會攔截系統選單的觸控，需修正而非調整測試。

同時補上新機制專屬的斷言：點擊背景收鍵盤、點擊互動控制項不收鍵盤。

## Implementation Contract

#### 行為

- 在任一有文字輸入的畫面，點擊該畫面的空白背景會收起鍵盤。
- 在任一有文字輸入的畫面，選取文字後點擊系統文字選單 (含貼上、選取、全選) 不會收起鍵盤。
- 點擊按鈕、切換開關、選擇器等互動控制項不會因此收起鍵盤，該控制項的原有行為照常執行。
- 可捲動的輸入畫面在捲動時收起鍵盤。
- 使用數字鍵盤的畫面可由鍵盤工具列的完成按鈕收起鍵盤。
- 鍵盤收起後，焦點狀態不再指向任何欄位。
- 上述行為在改寫前後對使用者一致。

#### 介面與資料形狀

- 新增共用的背景點擊收鍵盤修飾子，以泛型承載焦點綁定，不持有狀態。
- 綁定 store 的五個畫面在其功能狀態新增可選的焦點欄位，型別為可雜湊的欄位列舉。
- 不綁 store 的兩個元件在其內部持有焦點狀態。
- 移除 window 級手勢檔案及其匯出的修飾子；根視圖不再掛載該修飾子。

#### 失敗模式

- 背景層若未宣告可命中的形狀，透明區域不會接收觸控，點擊背景將無反應。
- 背景層若放置在內容之上而非之下，會遮蔽內容的觸控。
- 焦點狀態若在畫面關閉時未清除，重新開啟時會沿用上次焦點並意外彈出鍵盤。
- 綁定 store 的畫面若把焦點欄位留在視圖本地，會違反專案既有的呈現狀態規範，且無法被測試涵蓋。
- 捲動收鍵盤若採立即模式，使用者輕微捲動即收起鍵盤，體感突兀；互動模式讓鍵盤隨捲動漸進收起較符合系統行為。

#### 驗收標準

- ui-polish-and-safeguards 建立的回歸測試在改寫後繼續通過，未經修改。
- 新增測試斷言：點擊背景收鍵盤、點擊互動控制項不收鍵盤，兩者皆通過。
- 實機於七個導入焦點的畫面逐一確認：點背景收鍵盤、點控制項不收鍵盤、選取文字後點系統選單不收鍵盤。
- 實機確認捲動收鍵盤與數字鍵盤工具列完成按鈕仍可用。
- 全專案搜尋不到已移除的手勢型別與修飾子；iOS 與 iPadOS 皆建置成功。
- 以 TestStore 斷言綁定 store 的畫面在關閉時清除焦點狀態。
- 既有單元測試全數通過。

#### 範圍邊界

**在範圍內：** 共用背景點擊修飾子；七個畫面的焦點狀態導入與背景層套用；window 級手勢的完整移除；回歸測試的沿用與擴充；平台指引中相關硬規則的改寫。

**在範圍外：** 點空白收鍵盤這項行為的存廢；輸入流程與欄位順序的重新設計；訂單編輯表單的焦點狀態；新增鍵盤工具列到無數字鍵盤的畫面；搜尋列的收鍵盤行為。

## Risks / Trade-offs

- [背景層的命中測試若與既有版面互動衝突，可能遮蔽內容觸控或無法接收觸控] → 採背景修飾子內的透明填色搭配形狀宣告，從結構上位於內容之下；每個畫面導入後逐一實機確認既有控制項的觸控未受影響。
- [七個畫面逐一導入焦點狀態，工作量分散且容易漏項] → 任務依畫面切分並各自標明驗證方式；驗收時逐一對照 Implementation Contract 的行為清單，不以「整體感覺正常」作為通過依據。
- [改寫後若某處仍會攔截系統選單觸控，既有回歸測試會失敗] → 這正是該測試的用途。失敗時應修正新機制而非放寬測試。
- [本 change 依賴三個前置 change 的成果] → 任務第一組明確列出前置確認項目；前置未落地時不啟動後續任務，避免在移動的基礎上改寫。
- [移除全域手勢後，若有未被識別為輸入畫面的地方原本依賴它收鍵盤，該處會失去收鍵盤能力] → 導入前以文字輸入元件的使用位置逐檔清點，確認七個畫面涵蓋所有輸入情境；清點結果記錄於任務中作為完整性依據。
