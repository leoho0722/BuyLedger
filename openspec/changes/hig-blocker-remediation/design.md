## Context

HIG 合規審查在 apps/ios 找出 12 條 blocker。其中 6 條同源於 Design System 的語意色設計：BLTone 目前只有 foreground 與 background 兩支，foreground 同時被當成「文字色」與「色點色」使用，而 background 對非中性 tone 一律回傳 foreground 的 14% 淡底。這個設計讓「文字疊在自己的淡底上」成為必然結果，於是淺色模式下所有狀態膠囊都落在 1.96–3.35:1。

同一個混用問題也擴散到其他元件：計數徽章拿 foreground 當實心底色再疊白字、頭像用 runtime 算色的亮漸層疊白字、客戶排名徽章拿系統填色當底色疊白字、熱力圖拿強調色的透明度階梯當底色疊白字。這些都不是各自獨立的疏忽，而是「缺少一組『在這個底色上該用什麼文字色』的契約」所導致。

其餘 6 條分屬三個獨立根源：圖表元件從未接上無障礙 API、兩個關閉鈕的 padding 套在按鈕外側因而不擴大命中區、以及三處 UI 與實際系統狀態脫節。

現有約束：部署目標 iOS 18.0；snapshot baseline 位於 BuyLedgerTests 的快照目錄，配色變更會使既有 baseline 失效；所有新增 UI 字串必須同步補進字串目錄的英文值，否則英文模式會露出中文。

## Goals / Non-Goals

**Goals:**

- 讓語意色的「文字用途」與「圖形用途」在型別層面無法混用，使既有的誤用在編譯期就被攔下。
- 所有承載資訊的文字在 light、dark 與 Increase Contrast 三種情境下皆達到 4.5:1；單獨承載意義的圖形達到 3:1。
- 三個圖表元件對 VoiceOver 可讀，資料點具備名稱與數值，圖表具備整體摘要。
- 兩個關閉鈕在不改變視覺尺寸的前提下，命中區達到 44×44pt。
- App 不再呈現與實際系統狀態不符的 UI：沒有無後端支撐的控制項、載入失敗有原因與復原路徑、錯誤訊息對應真實失敗原因。

**Non-Goals:**

- 不處理審查報告的 49 條 warning 與 38 條 suggestion。
- 不把 BLPalette 整份改走系統色 API，僅修正 tertiaryLabel 被誤用於資訊文字的呼叫點。
- 不實作訂單提醒通知功能，僅移除無實作支撐的開關。
- 不改動頭像的色相演算法，僅調整明度。
- 不重造被審查點名為「重造系統元件」的分段控制、搜尋欄、進度條與清單列。
- 不為圖表加入互動選取或 Audio Graph 以外的探索功能。

## Decisions

### 語意色拆成 onSurface、indicator、onIndicator 三軌並移除 foreground

BLTone 現行的 foreground 承擔了兩種相互衝突的職責：作為文字色時需要對背景達 4.5:1，作為色點或進度條時只需達 3:1 且應維持鮮豔以利辨識。把兩者綁在同一個值上，等於強迫其中一方妥協。

改為三支各有明確受眾的方法：onSurface 供疊在卡片或列背景上的文字使用、indicator 供純圖形元素使用（色點、進度條、實心徽章底色）、onIndicator 供疊在 indicator 實心底色上的文字使用。background 保留但語意收窄為「搭配 onSurface 的淡底」。

關鍵決定是**移除 foreground 而非保留為別名**。移除後所有既有呼叫點都會編譯失敗，迫使實作者逐一判斷該用哪一軌——這正是要的效果，因為誤用無法靠靜態分析找出，只能靠人工判斷語意。若保留別名，既有的錯誤用法會靜默延續。

替代方案是保留 foreground 並新增 onSurface，讓呼叫端漸進遷移。否決原因是這會留下兩套並存的正確性標準，且沒有任何機制保證遷移完成。

### 色值來源改為 asset catalog Color Set，取代程式碼內的透明度推導

現行 background 以 opacity(0.14) 推導底色，這使得「底色」永遠是「前景色的淡版」，無法針對淺色模式獨立加深文字色。改為每個 tone 在 asset catalog 內定義四組具名 Color Set：文字色、淡底色、指示色、實心底上的文字色。

採 asset catalog 而非程式碼常數的理由：Color Set 原生支援 Any / Dark 外觀與 High Contrast variant 的三維組合，這是本次要滿足的達標矩陣；程式碼算色無法表達 Increase Contrast 這個維度，除非額外注入 colorSchemeContrast 環境值並在每個分支手動列舉。

指示色沿用現行 foreground 的色值（系統綠、橘、紅、藍、靛），不做調整——改動只會損失既有的視覺識別。

這些色值作為圖形元素的對比**並未**達到 WCAG 的 3:1 非文字門檻（light 外觀下系統綠對白底僅 2.22:1、系統橘 2.20:1），且色點實際疊在同色系淡底上，要同時保住「淡底」與「鮮豔色點」在數學上不可能達到 3:1。但這不構成問題：Apple HIG 的對比門檻表只約束文字（≤17pt 4.5:1、≥18pt 或 Bold 3:1），3:1 非文字對比屬 WCAG 1.4.11，其適用對象限於「理解內容所必需」的圖形。狀態膠囊一律同時渲染文字標籤，該標籤正是 HIG 明文要求的非顏色指示物，色點只是冗餘裝飾，故豁免 3:1 並標記為對輔助技術隱藏（HIG 對純裝飾圖形的指示即為隱藏而非提高對比）。驗收所用的 Accessibility Inspector 對比稽核本身也只評估文字，色點不在其判定範圍。

3:1 門檻仍適用於單獨承載意義的圖形，即進度條填色與圖表標記。

### 頭像維持色相演算法並壓低明度

頭像背景由名稱推導色相、以 runtime 生成漸層，這給了每位客戶一個穩定的專屬色，是既有的識別性設計。問題只出在明度太高導致白字不可讀。

決定只調整漸層兩端的飽和度與明度，使任意色相下白字都達 4.5:1，色相推導邏輯完全不動。替代方案是改用 asset catalog 內固定數量的預驗色盤，可控性更高但會讓不同客戶開始撞色，損失識別性。

### 熱力圖改用離散深度階梯，底色與前景色成對定義

熱力圖現行以連續的 opacity 0.2–1.0 疊強調色當底、固定白字。此結構在兩端都不可能達標：低透明度時白字幾乎消失，而最深的一端（不透明的系統藍）白字也只有 4.02:1。單純切換前景色無法解決，因為深色模式下不透明系統藍配白字同樣不足。

改為五級離散深度階梯，每一級的底色與其對應前景色在 asset catalog 內成對定義並各自驗過。離散化同時讓密度差異更容易辨讀——連續透明度在相鄰值之間本來就難以區分。

### 圈狀圖以類別維度驅動配色，取代直接指定色彩

圈狀圖現行把區段色彩以原始色值直接餵給 foregroundStyle，這讓 Swift Charts 無從得知區段的類別身分，因此不會生成任何類別語意，而區段名稱雖然收在資料模型裡卻從未被渲染。

改為以區段名稱作為 foregroundStyle 的類別維度，並以樣式對應表保住現有配色。這麼做讓 Swift Charts 自動把類別名稱帶進無障礙樹，是最小改動而語意最完整的路徑。長條圖無此問題（單一資料序列），僅需補資料點的名稱與數值。

### 命中區以固定尺寸框加形狀宣告撐開，視覺尺寸不變

兩個關閉鈕的 padding 都套在按鈕外層容器上，因此只增加版面間距、不擴大按鈕自身的命中區。修法是把尺寸與形狀宣告加在按鈕的標籤內部，讓命中區獨立於視覺尺寸；照片縮圖的刪除鈕另以位移維持原本貼齊角落的外觀。

不採「放大圖示視覺尺寸」的做法，因為那會改變既有版面比例，且審查明確指出視覺尺寸可以小於命中區。

### 載入狀態機補上失敗分支，不讓已載入旗標兼職

總覽頁與分析頁目前只判斷「是否已載入」，而載入失敗時該旗標維持為否，於是畫面停在載入中。根因是狀態機把「載入中」與「失敗」摺疊成同一個分支。

兩頁改為三分支判斷：已載入顯示內容、有錯誤訊息顯示失敗狀態與重試、其餘顯示載入中。錯誤訊息與重試動作沿用訂單功能既有的狀態與動作，不新增狀態欄位。

### 行事曆錯誤拆成權限被拒與建立失敗兩條路徑

現行的錯誤處理把權限請求失敗與事件建立、識別碼取得、連結寫入的失敗全部歸到同一個動作，於是所有失敗都顯示「請到設定開啟行事曆存取權限」。使用者在權限正常時被要求去改權限，照做也無法解決。

改為以權限請求的回傳值決定走哪條路：權限被拒維持現有的權限說明；其餘失敗走新增的建立失敗動作，訊息不提權限。

### 通知區塊連同偏好欄位一併移除

設定頁的通知開關背後沒有任何授權請求或排程實作，值只寫入偏好儲存後無人讀取。決定移除整個區塊，並一併清掉功能狀態、快照與儲存層的對應欄位——只移除 UI 而留下欄位，會讓下一位實作者誤以為功能存在。

## Implementation Contract

#### 行為

- 狀態膠囊、計數徽章、客戶排名徽章、頭像縮寫、熱力圖格內數字在 light、dark、以及各自的 Increase Contrast 情境下，文字對其實際背景的對比皆不低於 4.5:1。單獨承載意義的圖形（進度條填色、圖表標記）不低於 3:1；狀態膠囊的色點因旁有文字標籤而屬裝飾，豁免此門檻並標記為對輔助技術隱藏。
- 開啟 VoiceOver 後，走勢圖、長條圖、圈狀圖三者皆可被聚焦並朗讀出有意義的內容：長條圖與圈狀圖的每個資料點朗讀出名稱與數值，圈狀圖的區段名稱來自資料模型既有的名稱欄位；三個圖表各自提供一句整體摘要。若某圖表被判定為純裝飾，則必須明確標記為對輔助技術隱藏，不得維持現狀的「既無標籤也未隱藏」。
- 照片縮圖的刪除鈕與搜尋欄的清除鈕，命中區各方向不小於 44pt，且兩者的圖示視覺尺寸與現狀一致。
- 設定頁不再出現「通知」區塊與其開關。
- 訂單載入失敗時，總覽頁與分析頁顯示失敗說明（含來自訂單功能的錯誤訊息）與一個重試控制項；點擊重試會重新觸發訂單載入。載入成功後畫面恢復正常內容。
- 開團儲存時若行事曆權限被拒，維持現有的權限說明 alert；若權限已授予但事件建立、識別碼取得或連結寫入失敗，顯示不提及權限的建立失敗訊息。

#### 介面與資料形狀

- BLTone 對外提供 onSurface、indicator、onIndicator、background 四支計算屬性並回傳色彩；foreground 不再存在。四者皆**不接受色盤參數**——具名色彩資源由系統依當前 trait (外觀 + Increase Contrast) 自行解析，傳入色盤既無作用，還會誤導呼叫端以為色彩跟隨傳入值而非環境。
- asset catalog 內每個 tone 各有一組具名 Color Set，涵蓋文字色、淡底色、指示色、實心底上的文字色四種用途，每組皆定義 Any 與 Dark 外觀，並各自附 High Contrast variant。
- 熱力圖的深度以離散級數表示，每一級在 asset catalog 內有成對的底色與前景色 Color Set。
- 行事曆提醒失敗新增一個與既有權限被拒動作平行的動作；對應的提示文案在字串目錄內同時具備正體中文與英文值。
- 總覽頁與分析頁的失敗狀態不新增功能狀態欄位，沿用訂單功能既有的錯誤訊息與載入動作。
- 設定的通知偏好欄位自功能狀態、快照型別與偏好儲存層移除。

#### 失敗模式

- 色彩查詢一律走 asset catalog 具名資源。若資源缺失，SwiftUI 會回退為系統預設色而非崩潰——因此 Color Set 的新增必須與程式碼變更同批完成，不可分批合入。
- 圖表在資料為空時維持既有的空狀態行為，不因無障礙描述的加入而改變；空資料時的摘要應描述「無資料」而非朗讀零值。
- 重試動作失敗時再次顯示失敗狀態，不進入無限重試，也不清空既有的錯誤訊息。
- 行事曆的移除既有事件在事件已不存在時，維持既有的「視為無操作、不報錯」行為，不因錯誤路徑拆分而改變。

#### 驗收標準

- 全專案搜尋不到 BLTone 的 foreground 呼叫，且 iOS 與 iPadOS 皆可建置成功。
- 以 Accessibility Inspector 的對比檢查逐一驗過六個 tone 的膠囊、計數徽章、排名徽章三種名次分支、頭像的至少三個代表色相、熱力圖的五個深度級數，於 light、dark 與 Increase Contrast 下皆通過。
- 於實機開啟 VoiceOver，逐一聚焦三個圖表，確認朗讀內容符合前述行為描述。
- 於實機以 Accessibility Inspector 量測兩個關閉鈕的命中區不小於 44×44pt。
- 手動驗證：使訂單載入失敗（例如注入失敗的 repository），確認總覽頁與分析頁顯示失敗說明與重試，且重試可恢復。
- 手動驗證：在行事曆權限已授予的情況下使事件建立失敗，確認訊息不提及權限。
- 既有單元測試全數通過；受配色影響的 snapshot baseline 重錄後，差異僅限於預期的配色變化。
- 字串目錄的中英完整性測試通過。

#### 範圍邊界

**在範圍內：** BLTone 的方法拆分與其全部呼叫點的遷移；六個 tone 與熱力圖深度級數的 Color Set 新增；頭像明度調整；三個圖表元件的無障礙描述；兩個關閉鈕的命中區；tertiaryLabel 被誤用於資訊文字的呼叫點改為次要標籤色；設定頁通知區塊與其偏好欄位的移除；總覽頁與分析頁的載入失敗分支；行事曆錯誤路徑拆分；上述變更牽動的字串目錄與 snapshot baseline。

**在範圍外：** BLPalette 其餘手抄色值改走系統色 API；訂單提醒通知的實作；頭像色相演算法；元件重造類議題；審查報告的 warning 與 suggestion；既有 spec 內過時的平台目錄路徑修正。

## Risks / Trade-offs

- [移除 foreground 會使所有呼叫點一次性編譯失敗，若遷移判斷有誤會把錯誤從「對比不足」換成「語意用錯軌」] → 遷移時以「這個色彩最終疊在什麼底色上」為唯一判準：疊卡片或列背景走 onSurface、本身就是圖形走 indicator、疊在實心 tone 底色上走 onIndicator。遷移後逐一以對比檢查驗證，而非只確認編譯通過。
- [Color Set 資源缺失時 SwiftUI 靜默回退系統預設色，不會有編譯或執行期警訊] → 將 Color Set 新增與程式碼遷移放在同一批變更內完成；驗收時逐 tone 目視確認顏色符合預期，不以「畫面沒壞」作為通過依據。
- [配色變更會使既有 snapshot baseline 大量失效，可能掩蓋非預期的版面變化] → 重錄前先逐張檢視差異，確認變化僅來自配色而非版面；重錄後的 baseline 與程式碼變更一併提交。
- [加深後的狀態色會改變 App 的既有視覺調性，使用者可能感受到「顏色變濁」] → 只加深文字色，指示色（色點、進度條）維持現有鮮度，因此畫面的色彩重點不變，改變的只是小字的可讀性。
- [熱力圖從連續透明度改為離散級數，會改變既有的視覺呈現] → 這是刻意的取捨：連續透明度在相鄰值之間本就難以區分，離散化同時解決對比與可辨讀性；級數選為五級以在資訊量與可辨識度之間取得平衡。
- [移除通知偏好欄位若涉及既有使用者的偏好儲存，需確認不會影響其他偏好的讀取] → 移除前確認偏好儲存的序列化方式對未知或缺失欄位的容錯行為，避免既有使用者的其他設定被連帶重置。
