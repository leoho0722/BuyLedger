## Context

專案連結四個遙測相關產品（核心、分析、當機回報、效能監測），但程式碼中只有一行初始化呼叫，沒有任何自訂事件、使用者屬性或效能追蹤。也就是說目前收的全是各 SDK 的自動收集內容。

服務設定檔中的分析啟用旗標被設為關閉。經查官方文件，該平台控制分析收集的是應用程式自身資訊屬性清單中的一個鍵，以及一個會持久化並覆寫該鍵的執行期設定方法；服務設定檔中的旗標不是此平台的控制項。而本專案的資訊屬性清單沒有該鍵。因此分析收集實際上是開啟的。

同一份文件說明效能監測的自動埋點開關必須在遙測框架初始化之前套用，之後無法變更。

專案沒有隱私資訊清單。設定的持久化直接讀寫使用者預設值，屬於必須具名理由的 API 類別。

AI 總結送出的內容經查證為目前列表的商品明細，每行格式為類別、商品名稱、數量、單價與幣別，不含客戶姓名。

**後續決策（範圍收斂）**：本變更初版曾於設定頁新增「隱私」區塊，讓使用者可自行關閉遙測，並已完成實作與發布。使用者其後查核 `apps/ios/CLAUDE.md` 記載的產品前提——本 App 產物不對外散布、僅安裝於開發者自己的裝置——裁定該前提下不涉及第三方使用者的同意權議題，改為遙測**強制開啟、不提供使用者設定**，揭露只留在隱私資訊清單。本文件下方標示「（收斂後）」的段落記錄此次修訂；未標示的段落為原始決策，仍然有效。

## Goals / Non-Goals

**Goals:**

- 讓產物具備送審所需的隱私資訊清單。
- 讓遙測的設定真的生效，消除「看起來關了其實開著」的落差。
- 讓外送第三方的行為在動作發生處被誠實揭露。
- （收斂後）讓遙測收集狀態對照隱私資訊清單的宣告誠實一致：清單宣告的資料類型即為實際無條件收集的資料類型，不存在使用者可調整卻與清單描述不一致的中間狀態。

**Non-Goals:**

- 不移除任何遙測 SDK。
- 不改變遙測的預設狀態（原本預設開啟，收斂後維持開啟；改變的只是「是否提供使用者關閉入口」，不是預設值本身）。
- 不新增自訂埋點。
- 不改變外送內容。
- 不處理金鑰暴露。
- 不做首次啟動的同意流程。
- （收斂後）不提供使用者關閉遙測的入口；此為使用者基於「產物不對外散布」前提的明確裁定，非疏漏。

## Decisions

### 保留四個產品，改以補足透明度而非縮減蒐集面

移除未使用的 SDK 可以讓揭露面最小，但使用者選擇保留，理由是保留日後可能用到的彈性。

因此本變更的方向是補足透明度：清單如實宣告、設定真的生效、外送有揭露。代價是隱私資訊清單要宣告較多的資料類型與追蹤網域，而這些宣告目前對應不到任何實際用途；此點在文件中記錄，作為日後重新評估的依據。

### 以平台實際承認的機制控制收集，並移除誤導性的設定值

服務設定檔中的分析旗標在此平台無效。留著它比拿掉更糟：它讓讀者以為分析已關閉，於是不會再去檢查。

因此改用平台實際承認的機制：資訊屬性清單中的鍵決定啟動時的初始狀態，執行期設定方法在每次啟動時以固定值重申已啟用。同時移除或修正服務設定檔中那個無效的旗標，使設定檔不再暗示一個不存在的效果。

（收斂後）執行期設定方法原本設計為承載使用者的選擇並持久化；遙測改為強制開啟後，這個方法不再承載任何選擇，改為無條件呼叫、傳回固定的啟用狀態，見下方「遙測強制開啟，移除使用者可調整入口」。

### Performance 自動埋點必須早於框架初始化

效能監測的自動埋點開關無法在初始化之後變更。這條順序要求不因遙測改為強制開啟而鬆動——即使收集狀態是固定值，套用的時機仍然只有初始化之前這一次機會。

這與現行的初始化流程有次序衝突：目前初始化發生在應用程式代理的啟動回呼中。實作上讓套用自動埋點開關成為初始化流程的第一步。

介面測試模式的提前返回必須維持在最前面，否則測試會觸碰真實的 Firebase 專案（初始化及遙測呼叫）。

（收斂後）原始決策要求「遙測偏好的讀取必須早於框架初始化，且該讀取不得依賴尚未建立的相依注入容器」；遙測強制開啟後不再有偏好可讀，這項顧慮已隨之消失，但順序要求本身（自動埋點必須在 `FirebaseApp.configure()` 之前套用）維持不變，直接呼叫 `TelemetryClient.liveValue.enablePreInitializationCollection()` 取代原本先讀偏好再套用的兩步驟。

### 揭露文案與實際送出的欄位綁定

揭露若只寫「會送出訂單資料」，既不精確也無法驗證。使用者無從判斷客戶姓名是否被送出，而那正是最敏感的部分。

因此揭露必須逐項列出實際送出的欄位，並明說不含客戶姓名。規格另訂一條：送出欄位改變時揭露必須同批更新，使兩者不能各自漂移。

揭露採常駐呈現而非一次性提示：一次性提示只在第一次出現，而使用者可能在很久之後才想起要確認送了什麼。

此決策與遙測強制開啟無關，收斂後維持不變。

### （收斂後）遙測強制開啟，移除使用者可調整入口

原始決策讓使用者能在設定頁看到收了什麼並自行關閉。使用者其後裁定：`apps/ios/CLAUDE.md` 已記載本 App 產物不對外散布、僅安裝於開發者自己的裝置，因此不存在第三方使用者的同意權議題——提供一個只有開發者自己會用到的關閉開關，除了增加一個設定區塊與一組持久化欄位之外沒有實際保護對象。

因此設定頁的「隱私」區塊整段移除（header、開關、footer 說明），連同 `SettingsFeature.State.isTelemetryEnabled`、`SettingsSnapshot`／`SettingsStorage` 的對應欄位與 key、`BLAccessibilityID.Settings.telemetryToggle` 一併移除。揭露不再透過設定頁文字呈現，只留在隨產物出貨的 `PrivacyInfo.xcprivacy`（既有宣告內容不變，見下方 Risks 的說明）。

`TelemetryClient` 的兩個方法（設定 Performance 自動埋點、套用三支 SDK 執行期開關）原本帶 `Bool` 參數承載使用者選擇；強制開啟後若保留該參數，兩處呼叫點會恆傳 `true`，成為新的「零呼叫點殘留」（參數存在但值域只剩一種、不再有任何呼叫端傳入其他值）。因此改為無參數的 `enablePreInitializationCollection()`／`enableCollection()`，呼叫即代表「啟用」；`enableCollection()` 於每次啟動的初始化後都會呼叫，除了維持既有的「重申同一狀態」語意外，也確保覆寫掉裝置上任何殘留自舊版「可關閉遙測」時期的停用狀態（Analytics／Crashlytics 的執行期開關會持久化，只呼叫一次無法保證覆寫更早之前使用者曾經關閉過的紀錄；本專案產物僅安裝於開發者自己的裝置，此裝置確實可能殘留舊版關閉狀態）。

`TelemetryClient` 仍維持 `DependencyKey` 型式（`liveValue`／`testValue`／`previewValue`），與其餘 client 型別命名慣例一致；但已無任何 `@Dependency(TelemetryClient.self)` 消費者（原本唯一的消費者 `SettingsFeature` 已隨隱私區塊一併移除），`AppLaunchConfigurator` 一如既往直接呼叫 `.liveValue`（不經尚未建立的相依注入容器），因此 `BLUITestDependencyOverrides` 內原本覆寫 DI 容器內 `TelemetryClient` 的那一行也一併移除，避免寫入一個沒有任何讀取者的鍵。

隱私資訊清單（`PrivacyInfo.xcprivacy`）宣告的是「這些 SDK 可能收集的資料類型」，不是「使用者是否能關閉」；遙測本來就預設開啟，強制開啟後可能被收集的資料類型集合不變，因此清單內容本次不需要修改。

## Implementation Contract

**行為（使用者可觀察）**

- 設定頁不再出現任何遙測相關的區塊、開關或說明文字。
- 遙測於每次啟動皆強制套用為已啟用，不存在可停用的路徑；相依的 SDK 執行期狀態皆會被覆寫為啟用，包含裝置上可能殘留的舊版關閉紀錄。
- AI 總結的呈現處常駐一段說明，寫明送出的是目前列表的商品明細（類別、品名、數量、單價、幣別）到第三方雲端服務，且不含客戶姓名。
- 其餘行為不變。

**介面與資料形狀**

- 產物內含隱私資訊清單，宣告使用者預設值的具名理由，以及所連結遙測 SDK 的資料類型與追蹤網域。
- 資訊屬性清單保留控制 Analytics 收集初始狀態的鍵。
- 遙測不再有任何持久化偏好；`TelemetryClient` 的兩個方法皆不帶參數，呼叫即代表啟用。
- 服務設定檔不再保留無效的分析旗標。

**失敗模式**

- 介面測試模式：維持提前返回，不初始化遙測，也不呼叫 `TelemetryClient`。

**驗收標準**

- 對發行組態的產物檢查，隱私資訊清單存在於應用程式套件內。
- 清單宣告使用者預設值的具名理由，且宣告的資料類型與追蹤網域與實際連結的 SDK 相符。
- 以平台的診斷輸出確認三支 SDK 皆已啟用收集。
- 效能監測的設定在框架初始化之前套用，以流程順序的人工檢視佐證。
- 服務設定檔中不再存在無效的分析旗標。
- 設定頁不含任何遙測相關 UI，`isTelemetryEnabled`／`telemetryToggle` 於全樹零命中。
- AI 總結揭露的欄位清單與實際組出的內容逐項相符。
- 中英兩種語言下所有新增文案皆有對應字串；已移除的字串不殘留於本地化目錄。

**範圍邊界**

- 在範圍內：隱私資訊清單、遙測控制機制的修正、遙測強制開啟與相關 UI／持久化欄位的移除、AI 總結的外送揭露、相關文件同步。
- 不在範圍內：移除 SDK、改變遙測預設狀態、自訂埋點、改變外送內容、金鑰暴露、首次啟動同意流程、設定頁其他區塊。

## Risks / Trade-offs

- [保留四個產品使隱私資訊清單需宣告較多資料類型，而這些宣告目前無對應用途] → 於文件記錄此落差，作為日後重新評估的依據；宣告本身不會造成功能問題，只影響商店的隱私標示呈現。
- [移除服務設定檔中的無效旗標後，若日後有人依 Firebase 主控台重新產生該檔，旗標會回來] → 於平台指引記錄此點，並說明該旗標在此平台無效、真正的控制在何處。
- [揭露文案與送出欄位綁定，未來改動送出內容時容易漏改文案] → 規格明訂兩者必須同批更新；驗收要求逐項比對揭露與實際組出的內容。
- [關閉遙測後當機時將收不到任何堆疊]（收斂後已不適用）：遙測已改為強制開啟，不存在使用者可關閉的狀態，此風險項隨之消失。
- （收斂後）[介面測試模式的提前返回若被移除或搬到 `TelemetryClient` 呼叫之後，UI 測試流量會混入正式 Firebase 專案] → 提前返回維持在流程最前；驗收包含以介面測試執行一次確認未初始化 Firebase、未呼叫 `TelemetryClient`。
- （收斂後）[開發者自己的裝置可能殘留舊版「可關閉遙測」時期持久化的停用狀態，Analytics／Crashlytics 的執行期設定一旦寫入即覆蓋資訊屬性清單的初始值] → `enableCollection()` 於每次啟動皆無條件呼叫，以固定的啟用值覆寫任何殘留狀態，不依賴一次性遷移或使用者手動重設。
