## Context

開團的五條寫入路徑目前一致地先改畫面再寫入。失敗處理送出一個帶訊息的動作，該動作把訊息寫進畫面狀態的一個可選字串。實測全專案沒有任何呈現處讀取該欄位，因此所有開團寫入失敗在使用者端是完全無聲的。

刪除只做兩件事：自畫面狀態移除、自開團資料表刪除。訂單持有的開團名稱陣列、以開團識別碼關聯的提醒連結記錄、以及行事曆上以事件識別碼指向的事件，三者都不動。

提醒重建的既有順序是先刪後建。行事曆存取的失敗目前不分被限制、被拒絕與找不到可寫入的行事曆，共用一條訊息。

兩條刪除路徑（列表與詳情）的處理逐字重複，各自建構自己的確認對話框。

前一個變更已把開團名稱的唯一性檢查放在儲存流程的最前面、於寫入之前直接返回。本變更改寫同一段流程，必須保留該守門的位置與語意。

## Goals / Non-Goals

**Goals:**

- 讓開團的寫入失敗被使用者看見。
- 讓畫面顯示的開團狀態等於資料庫裡的內容。
- 讓刪除對話框對使用者的承諾在資料層被完整兌現。
- 讓提醒重建的中途失敗不留下指向已刪除事件的連結。
- 讓行事曆存取的失敗訊息指向使用者真正能採取的行動。

**Non-Goals:**

- 不改變以名稱字串關聯的結構。
- 不清理既有的孤兒連結與已殘留的行事曆事件。
- 不改動名稱唯一性與結單日判定（前一變更已完成）。
- 不改動提醒的設定方式與呈現形式。
- 不改動訂單側的寫入路徑。

## Decisions

### 移除無人讀取的訊息欄位，改以對話框承載一次性失敗

該欄位存在且被寫入，卻沒有任何呈現處讀取，這比沒有這個欄位更糟：它讓程式碼看起來有錯誤處理，實際上沒有。

改法與訂單側一致：一次性操作失敗以可呈現的對話框狀態承載，使用者關閉即消失；載入失敗維持既有的持續狀態呈現。兩者不共用承載，避免重演訂單那邊「清空點被載入旗標擋住」的問題。

刻意不採「把該欄位畫到列表上」這個最小改動，因為那只是把開團的失敗做成訂單原本的樣子，而訂單那邊正在改掉它。

### 刪除的連動清理與開團刪除在同一次操作內完成

刪除對話框告訴使用者「刪除這個開團」。使用者的理解是這個開團連同它在系統裡的痕跡都消失。目前只兌現了開團本身。

四件事必須一起成立：開團自資料表移除、該名稱自所有訂單的開團名稱陣列移除、提醒連結記錄移除、行事曆事件移除。前三者都在本機資料層，採單次操作落盤；行事曆事件在外部系統，無法納入同一個交易。

因此順序是：先完成本機三者的原子落盤，成功後才移除行事曆事件。行事曆移除失敗不回滾本機刪除，因為使用者要的是刪掉開團，而行事曆上的孤兒事件是可由使用者自行處理的次要問題；但該失敗仍須告知，不得靜默。

訂單側的名稱移除比照既有的改名連動實作，走同一條全表更新路徑，避免出現第二種寫法。

### 提醒重建改為先建後刪

既有順序是先刪舊事件再建新事件。中途失敗會留下一筆連結記錄指向已被刪除的事件識別碼，之後任何以該識別碼進行的操作都會落空。

改為先建立新事件、取得新識別碼並更新連結後，才刪除舊事件。這樣中途失敗最壞的結果是行事曆上多一則重複提醒，而不是資料層留下一個指向虛無的連結。多一則提醒使用者看得見也刪得掉，指向虛無的連結使用者看不見也處理不了。

### 兩條刪除路徑收斂為單一實作，但保留兩個呈現入口

兩條路徑的處理邏輯逐字相同，維護時必然只改一邊。收斂為單一實作。

但呈現入口必須保留兩個：列表與詳情在不同的版面層級，確認對話框需要掛在各自的層級才會出現在正確位置（iPad 的分割版面尤其明顯）。因此收斂的是處理邏輯與對話框內容的建構，不是呈現狀態本身。

### 行事曆存取的失敗分成三類

被限制與被拒絕對使用者的意義不同：後者可以自行到設定開啟，前者不行。找不到可寫入的行事曆根本不是權限問題，卻會走到同一條訊息，把使用者導向一個改了也沒用的設定頁。

三者各自給訊息。這與既有規格中「授權後的失敗不得走拒絕路徑」的原則同向，是把它的分類再細一層。

### 保留前一變更放在寫入之前的名稱守門

本變更把儲存流程從「先改後寫」翻轉為「先寫後改」，但名稱重複檢查必須維持在最前面、於任何寫入之前直接返回。

理由是重複名稱是可以在寫入前完全判定的條件，沒有理由讓它進入副作用；而且把它留在原位可以讓兩個變更的改動面不重疊。

## Implementation Contract

**行為（使用者可觀察）**

- 儲存開團、切換狀態、結團、從列表刪除、從詳情刪除，五條路徑在寫入成功後畫面才更新。
- 任一條路徑寫入失敗時，畫面維持原狀並彈出說明原因的對話框；關閉後不殘留任何錯誤文字。
- 刪除一個開團後：該開團消失、持有它的訂單不再顯示該開團名稱、其提醒連結不再存在、行事曆上的對應事件被移除。
- 行事曆事件移除失敗時，開團仍被刪除，但使用者收到告知。
- 修改提醒時間時，中途失敗不會讓提醒連結指向一個已不存在的事件。
- 行事曆存取被限制、被拒絕、找不到可寫入的行事曆，三者顯示不同訊息。

**介面與資料形狀**

- 畫面狀態不再持有那個無人讀取的訊息字串；一次性失敗以可呈現的對話框狀態表達，載入失敗維持既有表達。
- 刪除的本機部分以單次落盤完成，涵蓋開團資料列、訂單的名稱移除、提醒連結記錄。
- 行事曆存取的失敗以可區分的型別表達三種情境，而非共用單一訊息。

**失敗模式**

- 本機寫入失敗：畫面不變、對話框呈現原因、可重試。
- 本機刪除的三件事任一失敗：整體不生效，開團仍在。
- 行事曆事件移除失敗：本機刪除已生效不回滾，另行告知。
- 提醒重建中途失敗：連結指向的事件必定存在（新事件已建立），舊事件可能殘留，該情形須告知。

**驗收標準**

- 以注入失敗的儲存層執行五條路徑，畫面狀態逐一斷言未變且對話框出現。
- 刪除一個具有成員訂單與提醒的開團後，以持久層斷言三件事同時成立：訂單的開團名稱陣列不再含該名稱、提醒連結記錄不存在、行事曆客戶端收到移除該事件的呼叫。
- 本機刪除的三件事之一注入失敗時，斷言開團仍存在且訂單的名稱未被移除。
- 提醒重建過程中注入舊事件刪除失敗，斷言連結記錄指向的是新事件識別碼。
- 三種行事曆存取失敗各自對應不同訊息，有測試覆蓋。
- 前一變更的名稱唯一性與結單日測試維持綠燈。
- 全專案搜尋該訊息欄位零命中。

**範圍邊界**

- 在範圍內：開團五條寫入路徑的順序與失敗呈現、刪除的連動清理、兩條刪除路徑的邏輯收斂、提醒重建順序、行事曆存取失敗分類、對應規格與測試。
- 不在範圍內：以識別碼取代名稱關聯、既有孤兒連結與殘留事件的清理、名稱唯一性與結單日判定、提醒的設定方式、訂單側寫入路徑。

## Risks / Trade-offs

- [刪除的連動清理涉及三個資料表加一個外部系統，是本輪最大的單次改動，容易出現部分成立] → 本機三者以單次落盤保證原子性；行事曆事件明確排在本機成功之後且明文不回滾；驗收要求對「三件事同時成立」與「任一失敗則整體不生效」各有一條斷言。
- [行事曆事件移除失敗不回滾本機刪除，會留下行事曆上的孤兒事件] → 這是刻意取捨並在規格中明記：使用者要的是刪掉開團，而行事曆上的孤兒事件使用者看得見也刪得掉；反之若因外部系統失敗而讓開團刪不掉，使用者會陷入無法前進的狀態。失敗仍須告知。
- [先建後刪讓中途失敗可能在行事曆上留下重複提醒] → 相較於原本可能留下指向虛無的連結，重複提醒是可見且可自行處理的。此取捨在規格中明記。
- [兩條刪除路徑收斂後，若誤把呈現狀態也收成一個，iPad 分割版面的確認對話框會出現在錯誤層級] → 明確界定收斂範圍為處理邏輯與對話框內容建構，兩個呈現入口各自保留；驗收包含 iPad 版面的 UI 回歸。
- [本變更改寫的儲存流程正是前一變更剛加入名稱守門的位置] → 設計上要求守門維持在最前面、於寫入之前返回，兩者改動面不重疊；驗收要求前一變更的測試維持綠燈。
- [移除訊息欄位會讓既有引用該欄位的測試失敗] → 該欄位在生產程式碼零讀取點，測試若有引用即應一併改為斷言對話框狀態；此為預期的測試改動而非回歸。
