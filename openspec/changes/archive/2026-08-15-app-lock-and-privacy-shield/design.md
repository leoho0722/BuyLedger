## Context

App 目前沒有任何應用程式層的保護。全專案零本機驗證使用、零場景階段觀察，設定頁也沒有安全相關區塊。使用生物辨識所需的用途說明宣告尚未加入資訊屬性清單，缺少它會在請求驗證時直接終止應用程式。

畫面呈現的結構是：根視圖依尺寸分類選擇兩種版面之一，而其上有十餘個以浮層呈現的畫面，包含訂單編輯、合併流程、AI 總結、各式選擇器與照片檢視器。照片檢視器正是稽核點名情境中最可能被看見的畫面。

介面測試已有一套外部相依替身機制，涵蓋照片、行事曆與匯率三項，並以啟動旗標選擇行事曆的授權結果。

## Goals / Non-Goals

**Goals:**

- 讓使用者能以一個開關表達「這本帳需要保護」。
- 讓進入背景時畫面內容立即替換為鎖定畫面。
- 讓回到前景時需通過驗證才顯示內容。
- 讓開啟保護這個動作本身不可能把使用者鎖在外面。

**Non-Goals:**

- 不提供自訂密碼或 PIN。
- 不做逐畫面鎖定。
- 不做閒置逾時或背景停留門檻。
- 關閉開關時不保留任何殘留行為。
- 不改動檔案保護等級與設定頁其他區塊。
- 不做視窗層的遮蔽機制，不保證多工切換器快照排除內容 (見下方「範圍收斂」)。

## Decisions

### 單一開關同時控制上鎖與驗證

拆成兩個開關看似彈性較高，實際上兩半各自都不完整：只上鎖不驗證，回到前景時內容立即可見，等於沒有保護；只驗證不上鎖，離開前景時內容仍完整顯示在畫面上。使用者也難以判斷該開哪一個。

因此採單一開關，語意是「這本帳需要保護」而非「開啟某項技術機制」。關閉時完全回到現況，不留任何殘留行為，使關閉是一個乾淨的決定。

### 啟用前先驗證，失敗則不啟用

若開關可以在未驗證的情況下開啟，就會出現「使用者開了保護、下次啟動卻無法通過驗證」的狀態，而那在 App 內無法自救，只能重裝並失去資料。

因此把驗證放在啟用的路徑上：先驗證成功才寫入設定。驗證失敗、取消或裝置不支援時，開關回到關閉位置並以對話框說明原因。這讓「能開啟」本身就證明了「能進得來」。

### 範圍收斂：不做視窗層遮蔽機制

本設計原規劃遮蔽層掛在視窗層 (獨立 `UIWindow`)，理由是根視圖層的覆蓋蓋不到已呈現的浮層 (照片檢視器、訂單編輯、AI 總結等)，而那正是稽核點名情境最可能被看見的畫面。QA 審查發現該機制的觸發訊號 (`AppDelegate` 的場景生命週期回呼) 在 SwiftUI 場景式 App 中從未被呼叫，機制完全零生效且無測試偵測到；修正輪確認以 `\.scenePhase` 重新接線後機制本身技術上可行 (含變異驗證)。

使用者評估後決定收斂掉整個遮蔽層，只保留「進入背景即上鎖」：SwiftUI 端把畫面內容換成鎖定畫面 (`AppLockView`)，這段邏輯本就已有完整測試覆蓋並通過兩輪變異驗證，收斂後範圍與驗證能力對齊。代價是換成鎖定畫面的時機點與 iOS 系統擷取多工切換器縮圖的時機點兩者的先後順序無法保證，縮圖仍可能短暫含有背景化前最後一幀的內容 (見下方 Risks)；這是使用者知情下接受的取捨，不是本次收斂的疏漏。

替代方案 (逐浮層各自加遮蔽) 從未被採用：那是十餘處的重複，且新增浮層時必然漏掉。

### 驗證完全交由系統，不自建任何流程

自建密碼流程需要儲存與比對憑據，而那是一個 App 不該承擔的責任；系統的機制已涵蓋生物辨識與其失敗後的裝置密碼後備。

因此只呼叫系統的本機驗證，不儲存任何驗證憑據。設定中儲存的只有「保護是否開啟」這個布林值，它不是機密。

### 測試替身涵蓋驗證，並讓鎖定狀態可直接抵達

介面測試不能觸發真實的生物辨識提示，那是跨行程的系統介面。因此驗證納入既有的替身機制，並以啟動旗標選擇結果，使成功與失敗兩條路徑都能被測到。

另外讓「保護已開啟」的狀態可由啟動旗標直接設定，否則每個鎖定相關的測試都得先走一遍設定頁開啟保護，而那段流程本身又需要驗證替身，測試會變得冗長且脆弱。

### 解鎖按鈕依裝置生物辨識類型顯示對應名稱 (2026-08-02 追加)

初版鎖定畫面的按鈕文案是泛用的「重新驗證」，未反映裝置實際支援的生物辨識種類。使用者裁定改為「使用 Face ID 解鎖」／「使用 Touch ID 解鎖」，讓文案與 Apple 系統驗證彈窗本身的措辭一致。

**類型查詢介面**：`BiometricAuthClient` 新增 `biometryType: @Sendable () -> BiometryType`，與既有 `isAvailable`／`authenticate` 同層，讓 `AppLockFeature` 能以 `@Dependency` 注入不同機型於 TestStore 中驗證。`liveValue` 內以 `LAContext.canEvaluatePolicy(.deviceOwnerAuthenticationWithBiometrics)` 觸發求值後讀取 `biometryType`：`LAContext.biometryType` 依 Apple 文件僅在呼叫過 `canEvaluatePolicy` 後才會被填值，之前恆為 `.none`。映射 `LABiometryType` 四值 (`.none`／`.touchID`／`.faceID`／`.opticID`) 至本地 `BiometryType` 三值 (`.faceID`／`.touchID`／`.unavailable`) 的函式窮舉處理、不留 `default` 分支；`.opticID` 是 visionOS 專屬值，本專案裝置家族不會實際命中，但仍需明確列出才算完整處理。

**查詢時機**：查詢放在 `AppLockFeature` reducer 的 `appDidBecomeActive` 分支最前，而非另開新 action 或放進 `RootFeature.State.init`。理由：`appDidBecomeActive` 在冷啟動與一般返回前景時皆會觸發 (含保護已開啟、`isLocked` 由 init 同步設為真的冷啟動情境)，單一觸點即可覆蓋兩種情境；裝置的生物辨識硬體種類在單一裝置上不會於執行期變動，故不需要在每次背景化 (`appDidResignActive`) 都重查。代價是冷啟動且保護已開啟時，`AppLockView` 的第一格渲染會先用尚未更新的 `biometryType` 預設值 (中性文案)，`appDidBecomeActive` 幾乎立即接著觸發並更新；這個時間窗遠短於系統驗證彈窗本身出現所需時間，判斷為可接受的權衡，不值得為此另外改動 `RootFeature.State.init` 與其約 40 處呼叫點的簽章。**查詢本身不受 `isBiometricUnlockEnabled`／`isLocked` 閘門限制**——初版把查詢放在該 guard 判斷之後，只在保護已開啟且鎖定時才查詢；這個限制後續補做設定頁文案時證實是缺口，詳見下方「設定頁文案依機型顯示」節，`attemptUnlock` 的觸發仍維持原 guard 條件。

**無生物辨識時的中性退路**：規格「Unsupported device cannot enable protection」看似暗示鎖定畫面不會出現在無生物辨識的裝置上，但 `isAvailable` 檢查的是 `.deviceOwnerAuthentication` (biometrics 或裝置密碼任一即可)，故裝置僅設密碼、無任何生物辨識硬體時仍可通過啟用門檻並實際看到鎖定畫面。因此按鈕文案在 `biometryType == .unavailable` 時退回中性的「解鎖」，不得顯示空字串或「使用  解鎖」這類殘缺句子。

**文案放置點**：改的是鎖定畫面的按鈕標籤 (取代原「重新驗證」)，不是說明文字 (`請完成身份驗證以檢視內容。`)。按鈕是動作呼籲，指名將呼叫哪種驗證機制最貼切；說明文字是通用情境說明，不因機型而變，改了反而要為每種機型各寫一句、增加不必要的本地化負擔。同理，`enableToggled` 與解鎖流程送給系統驗證彈窗的 `reason` 字串維持不變：系統彈窗本身已依裝置類型自動顯示正確的圖示與名稱，`reason` 只負責說明「為什麼」而非「用什麼」，重複機型名稱屬冗餘。設定頁「帳本保護」開關的標籤與 footer 說明後續補上機型感知文案 (見下方「設定頁文案依機型顯示」節)；此段記錄的僅為鎖定畫面按鈕與系統驗證彈窗 `reason` 兩處的判斷，不涉及設定頁。

### 設定頁文案依機型顯示 (2026-08-02 補做)

初版僅改了鎖定畫面的解鎖按鈕，設定頁「帳本保護」區塊的開關標籤與 footer 說明維持泛用措辭 (見上節)。使用者指出這是範圍缺口：設定頁是使用者開啟保護前必經、也是最常見接觸這段文案的地方，泛用措辭與鎖定畫面的機型感知文案不一致。

**不改的理由不成立**：上一輪判斷不改的理由是「需要額外把 `BiometricAuthClient` 依賴拉進 `SettingsView`」；但 `SettingsView` 本已透過 `store: StoreOf<SettingsFeature>` 讀取 `store.appLock.isBiometricUnlockEnabled`，`store.appLock.biometryType` 同樣是既有欄位，不需要任何新依賴即可讀取。

**查詢閘門缺口 (真正需要修正的地方)**：`biometryType` 僅於 `appDidBecomeActive` 分支查詢，且原本被 `guard state.isBiometricUnlockEnabled, state.isLocked` 擋在前面，只有保護已開啟且處於鎖定狀態才會查詢。保護關閉 (預設狀態) 時這個 guard 恆為假，查詢從未執行，`biometryType` 永遠停留在建構時的預設值 `.unavailable`。這代表設定頁在使用者開啟保護「之前」——文案最需要正確顯示機型名稱的時刻——實際上只能看到中性退路文案，設定頁文案的機型感知形同虛設。修正方式：把 `state.biometryType = biometricAuthClient.biometryType()` 移到 guard 之前，讓查詢不受保護是否啟用影響；`attemptUnlock` 的觸發仍維持原 guard 條件。

**Toggle 標籤逐字重用鎖定畫面按鈕文案 (定案)**：使用者最初提出需求時已逐字引用「使用 Face ID 解鎖」／「使用 Touch ID 解鎖」。派工單寫「改成與鎖定畫面按鈕一致的點名方式」，這段措辭本身有歧義 (協調者原意是「都點名實際機型」，可合理讀成「字串逐字相同」)，歧義出在派工單措辭本身，非實作時的判斷失誤。`SettingsView` 的 Toggle 因此直接讀 `store.appLock.unlockButtonTitleKey`，不新增設定頁專屬的 Toggle 標籤屬性；`unlockButtonTitleKey` 同時服務鎖定畫面按鈕與設定頁開關兩處。footer 說明因為是完整句子、不是點名用語本身，仍新增獨立的 `protectionDescriptionKey` 計算屬性，命名與衍生方式比照 `unlockButtonTitleKey`；`SettingsView` 的 footer `Text` 讀此屬性，不在 View 內另寫 switch。

**已評估並否決的替代方案 (供日後對照，避免誤判為疏漏)**：協調者曾基於語意提出異議，主張 Toggle 標籤應改為與鎖定畫面按鈕文案各自獨立的版本 (Toggle 是開關、描述「這個功能是什麼」；按鈕描述「按下去會發生什麼動作」，兩者職責不同；逐字共用 `unlockButtonTitleKey` 會讓其中一處調整措辭時意外牽動另一處)。此異議已提交使用者裁定，使用者選擇維持逐字重用 (理由：使用者最初的要求本就逐字引用了該組字串)。**若日後有人看到 Toggle 標籤顯示「使用 Face ID 解鎖」覺得語意與「開關」角色不符而想改成獨立文案，這個選項已經評估過且已被使用者否決，不是疏漏，不建議重提，除非有新的理由。**

**文案內容**：Toggle 標籤顯示既有的「使用 Face ID 解鎖」／「使用 Touch ID 解鎖」，無生物辨識硬體時顯示「解鎖」；原「離開後鎖定並要求驗證」字串因此不再被任何程式碼使用，已自 `Localizable.xcstrings` 移除。footer 說明維持獨立句子，點名 Face ID／Touch ID，無生物辨識硬體時維持原文「需要通過裝置的生物辨識或密碼驗證」。

## Implementation Contract

**行為（使用者可觀察）**

- 設定頁出現「帳本保護」開關。
- 開啟時先要求驗證；成功則保護生效，失敗或取消或裝置不支援則開關回到關閉並顯示原因。
- 保護開啟時，進入背景即上鎖：畫面內容換成鎖定畫面。
- 保護開啟時，回到前景或冷啟動需通過驗證才顯示內容。
- 鎖定畫面的解鎖按鈕依裝置支援的生物辨識類型顯示對應名稱 (「使用 Face ID 解鎖」／「使用 Touch ID 解鎖」)；裝置無可用生物辨識硬體時顯示中性文案「解鎖」。
- 設定頁「帳本保護」開關的標籤與 footer 說明同樣依機型顯示對應名稱，且不論保護目前是否已開啟皆可見正確機型名稱；裝置無可用生物辨識硬體時顯示中性文案。
- 保護關閉時，上述行為皆不發生，與現況完全相同。
- 設定跨啟動持久。

**介面與資料形狀**

- 新增可注入的本機驗證相依，提供「是否可用」「請求驗證」與「查詢生物辨識類型」三項能力。
- 新增依場景階段轉送鎖定／解鎖動作的協調型別，讓這段接線可被單元測試直接驗證 (`Scene.body` 本身無法在測試中觸發)。
- 設定儲存新增一個布林偏好；不儲存任何驗證憑據。
- 資訊屬性清單新增生物辨識的用途說明。

**失敗模式**

- 啟用時驗證失敗、取消或不支援：不啟用、開關回到關閉、對話框說明原因。
- 解鎖時驗證失敗或取消：內容維持鎖定，提供再次驗證的途徑，不提供跳過。
- 缺少用途說明宣告：屬建置期缺失，驗收明列檢查項。

**驗收標準**

- 保護關閉時，離開與返回前景的行為與現況逐項相同。
- 保護開啟後進入背景，畫面內容換成鎖定畫面；此接線有單元測試覆蓋並通過變異驗證 (拔線後測試轉紅)。
- 啟用時驗證失敗與取消兩條路徑，開關皆回到關閉且出現說明對話框。
- 裝置不支援時無法啟用，且說明指出原因。
- 解鎖失敗時內容維持鎖定且可再次嘗試。
- 設定跨啟動持久，且冷啟動即進入鎖定狀態。
- 全專案搜尋確認無自建的密碼輸入流程與任何儲存的驗證憑據。
- 資訊屬性清單含生物辨識用途說明。
- 介面測試以替身執行，不出現任何系統生物辨識提示。
- 解鎖按鈕依裝置支援的生物辨識類型顯示對應名稱；無可用生物辨識硬體時顯示中性文案，不顯示空字串或殘缺句子；此行為以替身注入 Face ID／Touch ID／無三種類型分別驗證。
- 設定頁「帳本保護」開關標籤與 footer 說明依裝置支援的生物辨識類型顯示對應名稱，且保護尚未開啟時同樣可見；無可用生物辨識硬體時顯示中性文案；此行為以替身注入 Face ID／Touch ID／無三種類型分別驗證。

**範圍邊界**

- 在範圍內：單一開關、啟用前驗證、進入背景即上鎖、系統驗證的呼叫、測試替身與啟動旗標、用途說明宣告、解鎖按鈕與設定頁開關／footer 的機型感知文案。
- 不在範圍內：自訂密碼、逐畫面鎖定、閒置逾時、檔案保護等級、設定頁其他區塊、視窗層遮蔽機制。

## Risks / Trade-offs

- [多工切換器縮圖擷取時機與畫面換成鎖定畫面的時機先後順序無法保證] → 這是收斂掉視窗層遮蔽機制後的已知代價：進入背景後畫面內容確實會換成鎖定畫面 (有測試覆蓋)，但縮圖仍可能短暫含有背景化前最後一幀的內容。使用者知情並接受此取捨；若日後需要更強保證，須重新評估視窗層遮蔽機制 (技術上可行，先前已驗證)。
- [驗證失敗時若提供跳過途徑，保護即形同虛設] → 解鎖失敗只提供再次嘗試，不提供跳過；系統本身已提供裝置密碼後備，使用者不會真正被永久擋住。
- [缺少用途說明宣告會在請求驗證時直接終止應用程式] → 驗收明列檢查項；此為建置期即可確認的缺失，不會流到執行期才發現。
- [冷啟動即需驗證，會讓啟動流程多一步] → 這是保護開啟時的預期行為，且由使用者主動選擇；關閉時完全不受影響。
- [本變更新增的鎖定畫面需符合無障礙掃描守門] → 依既有次序約束，本變更排在無障礙覆蓋之後，該守門已上線並會涵蓋新增的畫面。
