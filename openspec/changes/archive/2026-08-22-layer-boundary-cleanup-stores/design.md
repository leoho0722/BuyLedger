## Context

根 store 目前在九個檔案被宣告：四個是根導覽宿主 (根畫面、兩個根版面、「更多」畫面)，五個是 feature 畫面 (總覽、分析、客戶、開團列表、開團詳情)。後五者因此可以任意讀取任何 feature 的狀態、直接送出任何 feature 的 action——開團詳情就是這樣讀取訂單清單並直接送出訂單 feature 的收款狀態 action。

客戶 feature 已示範正確作法：狀態只放一份唯讀的訂單投影，由根 feature 的變更監看同步。但它的 action 目前是空列舉，導覽仍走根 store。

分析區間目前住在根狀態，但它屬於分析 feature。

前置：檔案層的分層守門已由上一個 change 立起；本案要補的是 store 層的邊界。

約束：不改任何使用者可見行為，版面與可及性識別碼全部不動、基準圖不得重錄；不改客戶摘要的聚合口徑；不拆訂單 feature。

## Goals / Non-Goals

**Goals:**

- 五個 feature 畫面只吃自己 feature 的 scoped store
- 跨 feature 的意圖一律以 delegate 表達並轉發到根 feature 既有的導覽 case
- 分析區間回到分析 feature
- store 邊界由守門測試機器強制，例外以白名單常數鎖住
- 全程零行為變更

**Non-Goals:**

- 不改任何使用者可見行為、版面或可及性識別碼
- 不把「更多」畫面改成吃 scoped store
- 不動客戶摘要的聚合口徑
- 不拆訂單 feature
- 不把投影改用共享狀態機制

## Decisions

### D1 投影沿用根 feature 的變更監看，不引入共享狀態機制

跨 feature 的唯讀資料一律由根 feature 以變更監看單向同步到各 feature 的狀態，沿用客戶 feature 既有的模式。

共享狀態機制的採用範圍已在主檔單一來源那個 change 定為主檔目錄一處。本案是純結構、零行為變更的重構，夾帶新機制會讓發版時的回歸範圍講不清楚；且真正需要雙向同步的痛點在主檔副本，不在本案的唯讀投影。

投影一律唯讀語意：只有根 feature 寫、feature 端不得改，避免與訂單 feature 產生雙寫。

### D2 所有變更監看集中掛在同一處

投影數量從一份增加到四份 (客戶、開團、總覽、分析各持訂單投影，總覽與分析另持開團投影)，漏掛任一條就會出現「畫面顯示舊訂單而使用者無感」的靜默不一致。

因此所有變更監看集中掛在同一段、不散落，並補一條測試在單次訂單變動後同時斷言全部投影等值——日後新增第五份投影忘記掛就會失敗。

變更監看必須掛在 reducer 組合的外層，理由與既有註解說明的相同。

### D3 delegate 只轉發到根 feature 既有的導覽 case

四個新 delegate 一律轉呼根 feature 既有的導覽 case (開團選取、類別選取、客戶選取、新增訂單、分頁切換、訂單收款狀態變更)，不新增平行的根 case，每條分支就一行轉送。

這是為了避免本案把收斂掉的複雜度換個位置堆回根 feature。同時刪掉分析區間這個本不屬於根的屬性，讓根 feature 的淨行數增幅受控。

特別注意客戶選取這條：既有硬規則要求從「更多」分頁下的頁面深連結到別的根分頁時，必須先清空該分頁的導覽路徑再切分頁，否則 iPad 的分欄導覽會在分欄更新時崩潰。delegate 轉發後這條路徑仍須保持相同次序，並以測試守住。

### D4 delegate 只轉發，去重仍由訂單 feature 負責

畫面的載入 delegate 只做轉發、不自帶守衛，實際的重複載入去重仍由訂單 feature 的載入守衛負責。

因此驗收要明確斷言總覽的載入 delegate 會送出訂單與設定兩個載入 effect，並在實機從總覽冷啟動走一次確認資料有出來——五個畫面改吃 scoped store 後，載入的觸發時機是最容易出錯的地方。

### D5 語言走建構參數，不做投影

訂單畫面已建立「語言走建構參數」的既有慣例，四個畫面照抄。語言不做投影：它是純顯示用的參數，做成投影只會多一份要同步的狀態。

### D6 「更多」畫面列為白名單例外

「更多」畫面持有導覽路徑並在其目的地分派內為七個目的地各自建立子 store，做的事與兩個根版面完全同構，是導覽宿主而非 feature 畫面。

替代方案是為它新建一個持有導覽路徑與全部子狀態的 feature。已否決：那個 feature 的狀態依然要放七個子 feature 的狀態，型別上什麼都沒收斂，只是把根換個名字。改為列為白名單例外，並在檔頭與平台指引寫明理由，由守門測試的白名單常數把「例外只有這四個」鎖住。

### D7 store 邊界加進既有的分層守門測試

在上一個 change 建立的分層守門測試中新增一條斷言：掃描根 store 在 Features 下的宣告位置，與白名單常數逐一比對，多一個或少一個都失敗。

「少一個也失敗」是刻意的：白名單是精確集合而非上限，這樣某個根宿主被改寫或刪除時也會被發現，而不是靜默縮小。

## Implementation Contract

**行為**

- 使用者可見行為零變更：五個畫面的版面、可及性識別碼與互動全部不動
- 自總覽點開團、自分析點類別或開團、自客戶列點客戶、自開團詳情切換收款狀態，行為與改動前完全相同
- 分析區間在離開分析畫面後返回仍保持選取值 (兩個尺寸類別皆然)
- 自總覽冷啟動時訂單與設定資料正常載入，且不重複載入

**介面與資料形狀**

- 新增：總覽 feature (狀態持訂單、開團、月獲利目標、載入狀態四份唯讀投影；action 為載入、重試與 delegate，delegate 含重新整理、開團點選、新增訂單、檢視全部訂單) 與分析 feature (狀態持訂單、開團、載入狀態與自根狀態搬入的分析區間；action 綁定化以保留既有選擇器繫結寫法；delegate 含重新整理、開團點選、類別點選)
- 修改：客戶 feature 的 action 自空列舉改為含載入與客戶點選 delegate；開團 feature 的狀態新增訂單投影、action 新增收款狀態切換與對應 delegate；根狀態新增兩個子狀態並刪除分析區間；根 reducer 新增兩個範圍組合、擴充變更監看、新增 delegate 轉發分支
- 修改：五個畫面的 store 型別改為各自 feature 的 scoped store 並加語言建構參數；三個導覽宿主的目的地分派改傳 scoped store 與語言
- 修改：分層守門測試新增根 store 白名單斷言

**失敗模式**

- 漏掛任一條變更監看的症狀是畫面顯示舊資料且使用者無感，因此以「單次訂單變動後同時斷言全部投影等值」的測試作為機器守門
- 客戶選取的 delegate 轉發若未保持「先清空導覽路徑再切分頁」的次序，iPad 會在分欄更新時崩潰 (既有踩雷)，以專屬測試守住
- 基準圖若出現差異，先確認是否整張變色 (外觀設定) 或日期格式變化 (語系設定)，兩者皆非本次回歸，不得直接重錄

**驗收條件**

- 根 store 在 Features 下的宣告檔案恰為四個根導覽宿主，五個 feature 畫面零命中
- 守門測試的白名單斷言通過；移除白名單任一項即失敗
- 根狀態不再有分析區間屬性，且分析 feature 的區間有對應測試涵蓋
- 開團詳情全檔不再直接送出訂單 feature 的 action，收款狀態改經開團 feature 的切換 action 與 delegate 轉發，且有根 feature 測試斷言
- 新增「單次訂單變動同步全部投影」與「單次開團變動同步相關投影」兩條測試綠
- 客戶選取的 delegate 轉發保持先清空導覽路徑再切分頁的次序，有專屬測試守住
- 兩個新 feature 的 delegate 送出測試全綠，且不使用關閉窮舉的設定
- 主 scheme 全部單元測試綠，基準圖零重錄 (兩個受影響的基準測試只改 store 建構方式、版面一行未動)
- 介面自動化主回歸在兩個尺寸類別各一輪全綠 (識別碼與版面未動，應零改測試碼)
- iPhone 與 iPad 各 build 成功一次 (序列執行，build 前已遞增 build number)
- 自總覽冷啟動於實機走一次，確認資料正常出現

**範圍界線**

- 在範圍內：五個畫面的 store 邊界、兩個新 feature、兩個既有 feature 的邊界擴充、根 feature 的投影與轉發、分析區間歸屬、守門測試的 store 邊界斷言、對應文件與規格
- 不在範圍內：「更多」畫面、客戶摘要的聚合口徑、訂單 feature 的拆分、共享狀態機制、任何版面或可及性識別碼

## Risks / Trade-offs

- [五個畫面改吃 scoped store 後，載入的觸發時機改變，可能不載入或重複載入] → delegate 只做轉發、不自帶守衛，去重仍由訂單 feature 的載入守衛負責；明確斷言總覽的載入 delegate 會送出訂單與設定兩個 effect，並在實機自總覽冷啟動走一次
- [投影增加到四份，漏掛任一條變更監看會出現靜默不一致] → 全部變更監看集中掛在同一段、不散落；補一條測試在單次訂單變動後同時斷言全部投影等值，日後新增第五份忘記掛就會失敗；投影一律唯讀語意，只有根 feature 寫
- [根 feature 因新增 delegate 分支再度膨脹，把收斂的複雜度換個位置堆回去] → delegate 一律轉呼既有導覽 case、不新增平行 case，每條分支一行；同時刪掉分析區間這個本不屬於根的屬性
- [客戶選取的 delegate 轉發破壞既有的 iPad 分欄導覽崩潰防護] → 該路徑必須保持「先清空導覽路徑再切分頁」的次序，以專屬測試守住；這是既有踩雷，改寫時最容易漏
- [基準圖因外觀或語系漂移而誤判成本次重構的回歸] → 跑測試前先鎖模擬器淺色外觀；兩個基準測試改的只有 store 建構方式、版面一行未動，出現差異圖先確認是否整張變色或日期格式變化，兩者皆非程式碼回歸，不得直接重錄
- [白名單常數日後被隨手加項而失去約束力] → 白名單是精確集合，多一個或少一個都失敗；新增例外必須同時改測試與平台指引，於審查中被看見

## Migration Plan

不涉及持久化資料。本案只動 TCA 的執行期狀態形狀與畫面的 store 型別，不觸及任何持久化模型、版本化 schema 或遷移計畫，migration floor 與 target 皆維持現狀，既有使用者資料零影響。

順序約束：本案必須排在檔案層分層清理之後 (守門測試檔由該 change 建立)，也必須排在營收歸屬單一來源之後 (兩者都修改客戶摘要規格的同一條需求，本案的版本疊在其上)。

部署即一般發版，回退即還原程式碼，無殘留狀態。
