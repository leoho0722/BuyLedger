## Context

`OrderFilterSheet` 綁的是 `StoreOf<OrdersFeature>`，卻在自己的 `init` 內以 `store.state` 種下三個未套用選擇 (日期區間、商品類別、付款方式) 與一個捨棄確認旗標，另有搜尋文字 `@State` 與兩段 `localizedStandardContains` 過濾計算留在 View 的私有方法段。它以 `.sheet(isPresented:)` 掛在訂單清單的 compact 版面上，UI 測試側僅有一個從未被呼叫的開啟入口。

因此下列行為目前沒有任何自動化覆蓋：開啟 sheet 時未套用值是否正確自已套用值種下、選擇某列是否只動未套用值而不影響已套用篩選、套用時是否只提交有差異的欄位、以及有未套用變更時取消是否會出現捨棄確認。

四個 `Feature.State` 標了 `@unchecked Sendable`。查 SDK 與套件介面後確認：本地化字串資源在 Foundation 已有 Sendable 遵循、照片選擇項目型別本身即宣告為 `@unchecked Sendable`、TCA 的觀察註冊器為 `Sendable` 且呈現狀態、堆疊狀態、警示狀態皆有條件遵循。也就是說豁免的直接起因都已消失，但這是靜態推導、尚未實跑編譯。

訂單編輯 feature 有一個空 extension，且選擇器 route 的文件註解被錯貼到焦點欄位列舉上方。

另外，`order-filter-sheet` 規格與現況存在既有漂移：規格記載該 sheet 有日期區間與商品類別兩個 section，但程式碼另有付款方式 section；規格稱搜尋只過濾類別 section，實際上付款方式清單同樣被過濾。本次要修改的正是這幾條 requirement。

約束：不得新增字串目錄項目；不得改動導覽結構；`OrdersFeature` 已過大，本次不做拆分。

## Goals / Non-Goals

**Goals:**

- 篩選 sheet 的未套用選擇、搜尋文字與捨棄確認全部由 `OrdersFeature.State` 承載，整條流程可由 TestStore 斷言
- `OrderFilterSheet` 成為不持有任何呈現狀態的純呈現元件
- 四個 `Feature.State` 回到編譯器的 Sendable 檢查範圍，且「必須是 Sendable」成為編譯期契約
- 訂單編輯 feature 不再有空 extension 與錯位註解
- 篩選 sheet 的規格與實際 section 組成一致

**Non-Goals:**

- 不拆分 `OrdersFeature`
- 不改動選擇器的導覽結構
- 不統一其餘尚未顯式標註 `Sendable` 的 `Feature.State`
- 不新增任何本地化字串
- 不改動篩選 sheet 的可及性識別碼

## Decisions

### D1 未套用篩選採非 optional 值型別

`OrdersFeature.State` 以一個非 optional 的值型別承載三欄未套用選擇，而非可為 nil 的整體。理由：optional 會讓 View 端每一列的勾選判斷與搜尋輸入的綁定都要走 optional chaining，而巢狀綁定在 optional 下根本不成立。

代價是「sheet 關閉時未套用值恆等於已套用值」這條不變量由約定而非型別保證。緩解方式是把重種動作集中在開啟 sheet 這一處：每次開啟必重種，因此即使某條關閉路徑漏了回同步也不影響行為；再以捨棄與無變更取消兩條測試直接斷言關閉後的值，把約定固定成紅綠。

### D2 套用在 reducer 內直接提交，不轉派既有 action

套用時逐欄比對，有差異才寫回已套用欄位，任一欄變動則重算一次選取中的訂單。替代方案是回傳三個 effect 轉派既有的三個篩選 action，好處是重用已被覆蓋的分支；已否決，因為那需要三次 effect 往返、TestStore 要處理三個接收的順序，且選取中訂單會被連算三次。兩種作法的最終值完全相同。

「沒變就不提交」的既有語意以逐欄比對保住。

### D3 關閉一律由 reducer 決定

View 端移除 dismiss 環境值，四條關閉路徑 (套用、無變更取消、確認捨棄、以及未來任何新增路徑) 一律由 reducer 把 sheet 開關設為 false。這是讓整條流程進得了 TestStore 的關鍵：只要關閉還握在 View 手上，測試就無法觀察到 sheet 是否關閉。

### D4 捨棄確認改用 AlertState

捨棄確認自 View 的布林旗標改為 feature 持有的警示狀態，比照既有的刪除確認掛上對應的 `.ifLet`。沿用既有四句字面值，不新增字串目錄項目。警示狀態走的是同一套字串目錄，故英文模式的解析路徑不變。

### D5 先移除 @unchecked 再編譯，失敗才退回 wrapper

四個 State 逐一移除 `@unchecked` 並顯式標註 `Sendable` 後編譯。顯式標註而非完全不標，是為了把「這個型別必須是 Sendable」寫成編譯期契約；完全不標雖然隱式合成的結果相同，但那份保護是沉默的。

只有實際編不過的型別，才把該非 Sendable 成員抽成最小 wrapper，wrapper 宣告上方以一行註解寫明是哪個成員、為何跨執行緒安全，State 本身維持 `Sendable`。此步與篩選狀態下放無相依，可獨立完成，因此即使某一個編不過也不會卡住整個 change。

### D6 規格漂移一併更正而非沿用

兩條與 section 組成有關的 requirement，其標題本身就陳述了與現況不符的事實 (聲稱只有兩個 section、聲稱搜尋只影響類別)。這類標題會讓只掃標題的讀者得到錯誤結論，故以移除加新增的方式更名並改寫內容，而非保留標題只改內文。提交控制項那條的標題仍然準確，以修改處理。

此為本次改動被迫觸及的更正，不是額外擴張：既然必須改寫這些 requirement 的內容，就不能照抄一段已知與現況不符的敘述。

## Implementation Contract

**行為**

- 開啟篩選 sheet 時，三欄未套用選擇等於當前已套用的篩選值，搜尋輸入為空
- 在 sheet 內選擇任一列只改變未套用選擇，清單的已套用篩選與選取中訂單皆不變、sheet 不關閉
- 按套用時，只有與已套用值不同的欄位會被提交；任一欄有變動時選取中訂單重算為新篩選下的首筆；sheet 關閉
- 有未套用變更時按取消，出現提供捨棄與繼續編輯兩個選項的確認；選繼續編輯則 sheet 保留原有未套用選擇；選捨棄則未套用選擇回到已套用值且 sheet 關閉，已套用篩選全程不變
- 無未套用變更時按取消，sheet 直接關閉、不出現確認
- 有未套用變更時，互動式下滑關閉被阻擋
- 搜尋輸入即時過濾商品類別與付款方式兩份清單，日期區間清單不受影響；兩個清單的清除列在任何搜尋文字下都保持顯示
- 四個 `Feature.State` 的行為不變，僅並行安全標註改變

**介面與資料形狀**

- `OrdersFeature.State` 新增：承載三欄未套用選擇的巢狀值型別、篩選 sheet 搜尋文字、捨棄確認的呈現狀態、是否有未套用變更的計算屬性、兩份經搜尋過濾的清單
- `OrdersFeature.Action` 新增：三個未套用選擇的 action、套用、取消、以及捨棄確認的呈現 action 與其巢狀列舉；reducer body 尾端加上對應的 `.ifLet`
- `OrderFilterSheet` 移除：全部 `@State`、自訂 `init`、dismiss 環境值、以及四個私有計算與方法；可及性識別碼全數不變
- 四個 `Feature.State` 的 `@unchecked Sendable` 改為 `Sendable`

**失敗模式**

- 若某個 State 移除豁免後編不過，該型別退回 wrapper 方案，其餘三個仍完成；此情形須在 change 內記錄是哪個成員
- 測試 target 若出現警示狀態相關的連結失敗，依既有經驗屬 flaky，clean 後重跑；只有導覽目的地相關的符號才代表真程式碼問題，而本次不動導覽結構故不會引入

**驗收條件**

- `OrderFilterSheet` 內 `@State`、dismiss 環境值與自訂 `init` 的命中數皆為零，且該檔不再定義未套用變更判斷、套用並關閉、兩份過濾清單
- `apps/ios/BuyLedger/` 下 `@unchecked Sendable` 命中數為零；若因編譯限制保留，僅出現在專設的 wrapper 型別宣告上且上方有寫明理由的註解
- 訂單編輯 feature 無空 extension；route 說明位於其列舉上方，焦點欄位列舉上方只有焦點說明
- 新增七條篩選未套用流程測試全綠，且該段內不得出現關閉窮舉模式的設定 (這幾條全是純狀態變更、無並行 effect)
- TestStore 可完整走完：開啟 → 三個未套用選擇 → 取消 → 確認出現 → 確認捨棄 → 未套用值回到已套用值且 sheet 關閉，全程已套用篩選未變
- iPhone 與 iPad simulator 各 build 成功一次，主 scheme 全部單元測試綠
- 兩張訂單清單 compact 版面的 snapshot 未被重錄
- App 切英文語言後，捨棄確認的標題、訊息與兩顆按鈕皆顯示英文，且字串目錄無新增項目
- 篩選 sheet 三個預覽的勾選列與預覽傳入的日期與類別一致，未落回預設值

**範圍界線**

- 在範圍內：篩選 sheet 的未套用狀態與關閉流程、該元件的呈現狀態清除、四個 State 的並行標註、訂單編輯 feature 的空 extension 與註解位置、以及被迫觸及的篩選 sheet 規格更正
- 不在範圍內：`OrdersFeature` 拆分、導覽結構、其餘尚未顯式標註的 State、新增本地化字串、篩選 sheet 的視覺與可及性識別碼

## Risks / Trade-offs

- [未套用值與已套用值在 sheet 關閉期間失去同步] → 重種集中在開啟這一處，每次開啟必重種；並以捨棄與無變更取消兩條測試直接斷言關閉後的值
- [捨棄確認改用警示狀態後英文模式可能露中文] → 沿用的四句字面值已逐一確認存在於字串目錄的英文值；驗收明列切英文語言實測，並在提交前確認字串目錄未被建置污染 (既有踩雷：建置會寫入結構字串，需還原)
- [`OrdersFeature` 再長約九十行，加重既有的過大問題] → 新增的 case 相鄰擺放並以子分類註解集中，讓未來拆分是一刀可切的連續區塊；本次明確不拆，避免把純結構搬移的風險混入
- [移除豁免後某個 State 編不過而卡住] → 此步與篩選下放無相依，可獨立退回 wrapper 處理單一型別，不影響其餘三個與整體完成度
- [規格更名會失去該 requirement 的既有追溯區塊] → 追溯區塊由工具在封存時重建，且兩條標題本身陳述與現況不符的事實，保留標題的代價高於失去追溯連續性
- [(QA 修正輪補記) 「套用重算一次」的 scenario 缺乏機器守門] → 給定 `.filterApplyTapped` 目前的循序 `if` 區塊結構，任何「逐欄即時重算」的替代寫法在最終值上都與「全部比對完才重算一次」完全等價：最後一個真正觸發重算的 `if` 區塊執行時，其前面所有 `if` 區塊已套用完畢、其後面的 `if` 區塊本就未變動 (即已是最終值)，故重算次數在 `TestStore` 的 state 斷言下原理上不可觀察，這正是本節 D2 已建立的結論 (「兩種作法的最終值完全相同」)，不是測試遺漏。目前「once」僅由 D2 的設計紀錄與 code review 背書；要以機器驗證需改用可計數的間接層 (如把 `filteredOrders` 呼叫包一層可注入的 spy)，已超出本次「不拆分 `OrdersFeature`」的範圍界線，故不補此測試

## Migration Plan

不涉及持久化資料。本次只動 TCA 的執行期狀態、四個 State 的並行標註，以及註解與空宣告，完全不觸及任何持久化模型、版本化 schema 或遷移計畫，也不動跨平台 data model 與其生成檔。新增的未套用篩選值型別純屬執行期狀態、不落盤。App 冷啟動時篩選一律回預設值，此行為不變。

部署即一般發版，無資料遷移步驟；回退即還原程式碼，無殘留狀態。
