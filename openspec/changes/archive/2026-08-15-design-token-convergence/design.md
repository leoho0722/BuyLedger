## Decisions

### D1 (已撤除) 字級 token 軌道直接刪除

**本決策於 2026-08-01 撤除，不執行。** 原決策內容 (刪掉 `BLTypographyStyle` 列舉與 `BLTypographyModifier` 兩支檔，`BLCard` 預覽的三個呼叫改回系統字型) 建立在「字級 token 軌道生產呼叫點為零、僅 `BLCard` 預覽區塊三處」這個前提上。

**該前提已被本計劃自己的第 21 案 (`accessibility-coverage-sweep`) 完全反轉。** 該案的落地成果正是「把手寫字型指定收斂進 `BLTypographyStyle`／`blTextStyle(_:)`」，並在 `apps/ios/CLAUDE.md`「程式風格 Apple 補充」一節新增了規則：「字級一律走 `BLTypography` 的 `BLTypographyStyle` token、不手寫 `.font(.footnote)`／`.font(.title3.weight(...))` 等字面值」。2026-08-01 實測：`blTextStyle(` 呼叫點 117 處、橫跨 39 個檔，字級 token 已是專案標準寫法，不是零呼叫點的重造元件。

若仍執行原決策，刪除兩支檔會讓這 39 個檔全部編不過，等同摧毀第 21 案的成果並讓平台指引寫的規則與程式碼互相矛盾。**本案因此不刪除、不擴充字級 token 軌道，維持現狀**，`BLTypography.swift`／`BLTypographyModifier.swift`／`BLCard` 的預覽字級皆不變動。

原決策的替代方案討論 (擴充列舉並把手寫字型全部改過去) 已隨此撤除一併作廢：字級 token 的擴充/收斂範圍已由第 21 案處理完畢，不在本案重新規劃。

> 是否要為字級加一條掃描守門 (如「剩餘手寫 `.font(` 需有記錄理由」)，本設計文件不代替協調者拍板；見 tasks.md 任務群組 7 的附帶建議段落。

### D2 次要文字改走 Color 擴充的單一入口

在顏色擴充檔新增一支靜態屬性代理到色盤的次要標籤色。刻意放在顏色型別的擴充上而非色盤上，是為了讓呼叫端不必在 20 餘個私有 `@ViewBuilder` helper 內各自取得色盤實例，那會製造大量與本次無關的差異。此作法比照專案既有的按鈕樣式工廠慣例。

**2026-08-01 施工中發現的技術修正：呼叫端一律用 `Color.blSecondaryLabel` 明確型別形式，不用 `.blSecondaryLabel` 前置點縮寫。** 原決策文字設想呼叫端可用前置點縮寫 (implicit member 語法) 直接取代 `.secondary`，實際套用時發現這在本專案的 `foregroundStyle(_:)` 呼叫情境下**必然無法解析**：56 處呼叫點中有 6 處 (`BLCard.swift`／`BLTagPill.swift`／`AISummaryView.swift` 3 處／`AppLockView.swift`) 用前置點縮寫時編譯失敗 (`type 'ShapeStyle' has no member 'blSecondaryLabel'`)，其餘看似成功實為批次編譯尚未觸及；改用明確的 `Color.blSecondaryLabel` 後全數編譯通過。

**2026-08-01 QA 修正 (技術成因重新診斷)：** 上一版文字把此現象歸因為「implicit member 型別推導在特定 view builder 巢狀深度下不穩定，屬 Swift/SwiftUI 型別檢查器已知限制」，經查證**這是誤診**。`blSecondaryLabel` 是掛在 `extension Color` 上的靜態屬性，而 `foregroundStyle(_:)` 收的參數型別是 `some ShapeStyle`；implicit member 語法只會在參數的宣告型別上尋找對應靜態成員，`ShapeStyle` 本身並無 `blSecondaryLabel`，故編譯器回報「`type 'ShapeStyle' has no member 'blSecondaryLabel'`」是正確且**確定性**地報告成員不存在，不是型別檢查器在特定巢狀深度下的不穩定行為。要讓前置點在此情境下可解析，需改寫成 `extension ShapeStyle where Self == Color { static var blSecondaryLabel: Color }` (比照本專案既有的按鈕樣式工廠慣例 `extension ButtonStyle where Self == BLButtonStyle`，見 `BLButtonStyle.swift:111`)；本案選擇不做這項改寫，因為它會牽動全部 56 個呼叫點與非 snapshot 範圍的大量檔案，改動面與本案「維持形狀不變、只換入口」的目標不成比例。為求一致，全部 56 處呼叫點統一採明確型別形式 `Color.blSecondaryLabel`，不混用兩種寫法。

### D3 Section footer 一併收回，不留豁免

表單與清單的 section footer 一併換走色盤的次要標籤色。footer 承載的是「總收款如何計算」這類真正的規則說明，屬資訊性文字、適用 4.5:1 地板。

代價要講清楚：footer 說明文字會比系統預設明顯變深，與同一表單內的標頭產生深淺差，這是使用者看得到的外觀變更。相對地，明文豁免會讓掃描守門必須帶白名單，而列舉式白名單正是本次要消滅的老毛病。

落地順序上先只改一個畫面的三處、實機目視確認可接受後再全庫套用；若判定過深，退路是微調色盤次要標籤色的推導係數並重跑對比測試，而不是回頭保留系統值。

### D4 色彩字面值的唯一例外是 white black clear

系統強調色、系統綠、系統橘 (含滑動操作)、系統紅與系統藍等具名系統色字面值全部改走色盤 (含元件預覽區塊)；零呼叫點的十六進位建構子刪除。白、黑與透明維持字面值，因為漸層上的白字、遮罩與透明背景不是語意色、不隨外觀解析。這條例外同時寫進規範與掃描器，避免下次被當成漏網之魚而「順手修正」。

**2026-08-01 校準補充 (2026-08-01 QA 修正)：** 原決策文字僅點名「系統強調色、系統綠、系統橘」三類，是提案當時實測到的具體違規清單。**十六進位建構子的移除屬既有規則涵蓋**：`color-system-foundation` 規格在本案之前的正文本就禁止「手抄十六進位字面值」與「色盤維持亮暗分支」兩件事，這部分並非本案新增。但「具名系統色一律不得取代色盤色，唯一例外白黑透明」這句規則本身是本案這份 delta 才新寫入規格正文；本案之前的規格正文從未提及具名系統色。強調色／綠／橘三類在提案階段即已依此新規則納入範圍，2026-08-01 重新量測另外發現的系統紅 5 處、系統藍 2 處與 `plainBackground` 2 處同樣屬於這條新規則涵蓋的範圍擴張，與強調色／綠／橘同性質，一致性上合理納入。這不應被誤讀為「規格早已涵蓋、本案只是補測」；正確理解是本案新寫的規則本就涵蓋全部具名系統色，紅／藍／`plainBackground` 是同一次擴張範圍內遲了幾天才盤點到的實例，不是另一輪新擴張。`Core/Testing/BLUITestDependencyOverrides.swift` 的 `photoPalette: [UIColor]` 例外處理見 Context 一節。

### D5 狀態色點承認為獨立 token 軌道

新增一支專門承載分組色相的來源，以窮舉分支把狀態映到色盤色，並在文件註解寫明分軌理由：語意色軌道表達語意強度 (6 值)、色相軌道表達流程階段的可區分性 (8 值)；狀態膠囊一律走語意色，只有側邊欄分組色點走色相軌道。側邊欄原本內嵌的映射整段刪除改為呼叫這支來源，視覺零變更。

替代方案是全部改用語意色軌道。已否決：映射後兩個相鄰狀態同色，會被讀成渲染 bug，需另給區分手段才能採用。真正要解決的是「這套映射沒有單一來源也沒有說明」的治理問題，收進 Design System 並寫明理由即已達成。

### D6 掃描守門以測試內的原始碼掃描實作

新增一支測試檔，以自身檔案路徑往上定位專案原始碼目錄，列舉全部 Swift 檔 (排除生成檔目錄)，每個檔先剝除行註解與雙引號字串字面值再比對，避免把註解或本地化文案誤判為違例。

不引入外部靜態分析工具的理由有三：其規則表達力做不到「某個 API 只准出現在特定檔案」這種帶檔案條件的判斷；要新增設定檔、建置階段與一支需維護版本的外部相依；而獨立腳本在目前沒有 CI、也沒有 git hook 的現況下等於又回到靠人記得跑。測試內掃描則隨主 scheme 測試自然被執行，且違例訊息能直接引導到正解。

需要例外時走具名的豁免標記並要求填寫理由，該理由非空本身也是一條斷言，且測試訊息會把當前全部豁免列出來，讓豁免無法悄悄累積。

### D7 刪除從未讀取的 colorScheme 宣告

逐檔刪除未被讀取的外觀環境宣告與其文件註解，只保留卡片陰影修飾子那一個真正的讀者。已逐檔確認這些檔案內該符號只出現一次 (宣告本身)，屬純刪除、無行為變更。色盤與語意色軌道全走系統動態色與資源目錄，外觀切換由系統驅動，view 不需自行宣告依賴。

- 分組色相測試綠：側邊欄實際顯示的 8 色在四種外觀下兩兩相異；「每個訂單狀態都有對應色」由窮舉 switch 的編譯期保證涵蓋，不另立執行期斷言 (2026-08-01 施工中修正：對應的執行期斷言會是無意義的假測試，理由見 tasks.md 6.2)
- 主 scheme 全部單元測試綠 (含重錄後的 5 張基準圖)；介面自動化主回歸在 iPhone 與 iPad 各跑一輪全綠
- iPhone 與 iPad 各 build 成功一次 (序列執行，build 前已遞增 build number)
- **不要求**：平台指引中字級修飾子的敘述不變動 (D1 已撤除，字級 token 規則仍有效、不刪除)；Design System 準則新增本次色彩／掃描守門相關的敘述

**範圍界線**

- 在範圍內：次要文字入口、色彩字面值收回 (含新查出的紅／藍)、分組色點單一來源、未讀取宣告清除、掃描守門、對應文件與規格
- 不在範圍內：**字級軌道刪除或擴充** (D1 已撤除)、第三層文字色、白黑透明字面值、外部靜態分析工具、可及性識別碼、任何版面或互動行為

## Risks / Trade-offs

- [56 處次要文字一次變深，偏離平台預設外觀且無法只靠基準圖判斷好壞] → 先只改設定頁 (實測 6 處) 目視比對確認可接受再全庫套用；重錄基準圖時新舊並排檢視而非直接覆蓋。若判定過深，退路是微調色盤推導係數並重跑對比測試，不回頭保留系統值
- [掃描測試把註解、字串字面值或本地化文案誤判為違例] → 比對前逐行剝除行註解與成對雙引號內容；套用修正前先在未改動工作樹跑一次，要求回報數字與逐項量測吻合，對不上先判斷是掃描器寫錯還是基準過時 (本案經過 25 個 change 疊加，基準過時是預設答案)
- [「系統取色介面只准出現在色盤檔」日後擋住合法的新系統色需求] → 這正是規則要的行為：失敗訊息直接引導成一次數行的色盤擴充；真有非色盤情境時走具名豁免標記並填理由，於審查中被看見
- [刪掉 16 個外觀宣告後某處其實靠它觸發重繪] → 已逐檔確認該符號全檔只出現一次，不存在讀取點；刪除後兩平台各 build 一次，並於實機切換深淺色目視確認卡片陰影仍正確
- [一次動 20 餘檔與 5 張基準圖，中途方向若改變回退成本高] → 步驟排成每一步結束都能單獨 build 綠的順序 (新入口 → 換呼叫點 → 清宣告 → 分組色點 → 守門 → 文件)，前三步彼此無耦合可分段驗證；掃描守門刻意排在最後，避免規則先落地卻擋住自己的施工
- [分組色相成為第二套色彩詞彙，日後可能被誤用在狀態膠囊上] → 新來源的文件註解明寫兩軌的適用邊界，掃描守門之外另以規格的情境把「語意色軌道 6 值不足以區分 8 個流程分組」這個已知限制記錄下來，避免下次有人再各寫一套
- [D1 撤除後，字級軌道本身仍缺乏掃描守門，剩餘手寫 `.font(` 字面值可能持續增加] → 本次不擴大範圍自行決定；已於 tasks.md 任務群組 7 附帶建議，留給協調者裁定是否另開範圍

## Migration Plan

不涉及持久化資料。改動範圍限於 SwiftUI View、Design System、共用擴充、測試與文件，沒有任何持久化模型、版本化 schema、遷移階段或容器建構的變更，因此不需新增 schema 版本、不動 migration floor、也不需凍結新的影子型別。同樣不涉及跨平台 data model 與其生成檔，提交前不需跑生成檔同步檢查。

既有使用者資料零影響。使用者能感知的差異只有次要說明文字變深一項；分組色點視覺零變更。

部署即一般發版，回退即還原程式碼，無殘留狀態。
