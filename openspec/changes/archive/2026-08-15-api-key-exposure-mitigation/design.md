## Context

兩把金鑰的注入鏈是：本機建置設定檔填值，經專案設定掛到應用程式目標，資訊屬性清單以變數引用，建置時值寫入清單，執行期自套件讀回。建置設定檔未入版本庫。

金鑰為開發者自有，產物只安裝於開發者自己的裝置。因此「金鑰隨產物出貨」的暴險前提（產物可能落到他人手上）在本專案不成立，金鑰的提供方式維持現狀。

匯率服務的認證目前把金鑰放在網址路徑中。網路層韌性的變更已移除錯誤訊息中的網址內插，但網址本身仍含金鑰。

專案沒有任何地方記錄「內嵌金鑰是已評估並接受的風險」，也沒有記錄金鑰的撤換程序。

## Goals / Non-Goals

**Goals:**

- 讓金鑰不再出現在網址中，消除與產物散布無關的那條洩漏途徑。
- 讓「內嵌是知情取捨」成為有記錄的決定，含其成立前提與失效後的作法。
- 讓金鑰疑似外洩時有可照做的撤換程序。

**Non-Goals:**

- 不改變金鑰的提供方式。
- 不引入後端代理。
- 不加密或混淆內嵌金鑰。
- 不改變端點、參數或回應處理。
- 不代為撤換金鑰。
- 不改動既有的未設定金鑰空狀態。

## Decisions

### 維持建置期注入，把風險記錄為有前提的接受

改為執行期提供（使用者輸入、鑰匙圈存放）能讓產物完全不含金鑰，但那解決的是「產物落到他人手上」這個問題，而該情形在本專案不成立：能取得產物的人就是持有金鑰的人。為一個不成立的威脅付出設定入口、鑰匙圈封裝與跨組態解析順序的成本，是不划算的。

因此維持現狀，但把它從「沒人提過的預設」變成「有記錄的決定」。記錄必須包含前提，否則它會退化成一句沒有效期的免責；也必須包含前提失效時的作法，否則未來真要散布時仍要從頭推導。

### 金鑰移出網址，理由與產物散布無關

這一項與上一項是不同的問題。網址中的金鑰會被系統的網路記錄留存、被代理設施記錄，也會在複製請求或回報問題時被一併帶出。這些途徑不需要任何人取得產物。

因此即使接受了內嵌，仍應把金鑰移出網址。服務端支援 Bearer 權杖標頭認證已由使用者確認，因此改法明確：憑證改以授權標頭攜帶，端點路徑不再含憑證段。此改動不影響任何回應處理。

### 撤換程序寫成可照做的步驟，而非原則

「外洩就換金鑰」是原則，不是程序。真的發生時需要知道去哪裡換、換完之後要做什麼才會生效。

本專案的金鑰是建置期注入的，因此換發之後必須重新建置並重新安裝才會生效——這一點與執行期提供的作法不同，值得明寫，否則會以為換完就結束了。

## Implementation Contract

**行為（可觀察）**

- 匯率請求的網址不再含金鑰，認證出現在請求標頭。
- 其餘所有行為不變，包含未設定金鑰時的既有空狀態。
- 使用者面沒有任何可見變化。

**介面與資料形狀**

- 匯率請求的組裝改以標頭攜帶憑證；端點路徑不再含憑證段。
- 金鑰的解析介面與來源皆不變。

**失敗模式**

- 與現況相同。認證方式的改變不新增任何失敗路徑；憑證無效仍映射為既有的憑證無效分類。

**驗收標準**

- 組出的匯率請求網址不含憑證，授權標頭以 Bearer 形式攜帶之，有測試覆蓋。
- 全專案搜尋確認無任何位置把憑證內插進網址、日誌、錯誤訊息或診斷輸出。
- 平台指引可查到內嵌金鑰的風險接受記錄，含成立前提與前提失效時的作法。
- 平台指引可查到撤換程序，且明載換發後需重新建置與安裝才生效。
- 主 scheme 全套單元測試綠燈。

**範圍邊界**

- 在範圍內：匯率認證的傳遞方式、憑證不進入輸出的確認與守門、風險接受與撤換程序的記錄。
- 不在範圍內：金鑰的提供方式、鑰匙圈、設定頁入口、後端代理、加密內嵌、端點與參數、既有空狀態。

## Risks / Trade-offs

- [端點路徑形狀改變後，既有的網址組裝與其測試會一併失效] → 網址組裝與認證一併改動並由同一批測試覆蓋；驗收要求以實際請求確認匯率仍能正常取得，而非只看單元測試。
- [風險接受的記錄可能被當成永久免責] → 記錄必須寫出前提與失效條件；規格明訂「未記錄的內嵌不得僅因無人反對而視為已接受」，使它是一個有條件的決定而非空白支票。
- [未來若對外散布產物，前提失效但沒人會注意到] → 前提與其失效後果一併寫入文件與規格；規格另立一條情境明訂散布即使接受失效，讓後續稽核能直接指出。
- [縮減範圍後，稽核原本標為中度的風險看起來像被忽略] → 縮減的理由與其前提在提案中明寫，而非默默降級；若前提有誤，該記錄本身就是最容易被質疑並更正的地方。
