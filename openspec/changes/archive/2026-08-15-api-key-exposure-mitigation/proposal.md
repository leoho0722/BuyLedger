## Why

兩把 API 金鑰經由建置設定注入資訊屬性清單，執行期自套件讀回。金鑰是開發者自己的，建置設定檔未入版本庫，產物只安裝在開發者自己的裝置上。

在這個前提下，「金鑰隨產物出貨」的實際暴險接近零：能取得產物的人就是持有金鑰的人。稽核把它評為中度風險，是以「產物可能落到他人手上」為假設；該假設在本專案目前不成立。因此**金鑰的提供方式維持現狀，不改為使用者自帶、不引入鑰匙圈、不新增設定頁輸入入口**。

但仍有兩件與提供方式無關、值得處理的事：

**金鑰出現在網址中。** 匯率服務的認證是把金鑰放在網址路徑。網址會被系統網路記錄、代理伺服器與診斷輸出留存，也更容易在貼上請求或回報問題時被連帶複製出去。這條洩漏途徑與「產物是否落到他人手上」無關，改走請求標頭即可消除。

**沒有記錄這是一個知情的取捨。** 目前沒有任何地方寫明「金鑰內嵌是已評估並接受的風險」及其成立前提。下一次稽核會再報一次同樣的發現，而未來若真的對外散布產物，也沒有任何東西提醒這個前提已經不成立。

## What Changes

- 匯率服務的認證由網址路徑改為 Bearer 權杖標頭，使金鑰不再出現在網址中。服務端支援此認證方式已由使用者確認。
- 明文記錄金鑰內嵌是已評估並接受的風險，並寫出它成立的前提：產物不對外散布、金鑰為開發者自有。同時記錄前提失效時應採取的作法，使日後真要散布時不必重新推導。
- 記錄金鑰的撤換程序：外洩或疑似外洩時如何在服務商後台換發、以及換發後需重新建置與安裝。
- 確認全專案沒有任何位置把金鑰寫入日誌、錯誤訊息或診斷輸出。錯誤訊息的部分已由網路層韌性處理，本變更只做確認與守門。

## Non-Goals

- 不改變金鑰的提供方式。維持建置設定注入，不改為使用者自帶、不使用鑰匙圈、不新增設定頁輸入入口。
- 不引入後端代理。
- 不加密或混淆內嵌的金鑰。既然暴險前提是產物不外流，加密只增加複雜度而不改變任何結論。
- 不改變端點、參數或回應處理。
- 不代為撤換金鑰，只記錄程序。
- 不改動未設定金鑰時的既有空狀態。

## Capabilities

### New Capabilities

- `api-key-handling`: 金鑰處理的契約，涵蓋憑證不得出現在網址、不得進入日誌與診斷輸出，以及內嵌金鑰作為知情取捨時必須記錄的前提與失效條件。
