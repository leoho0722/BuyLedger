## 1. Core 上行依賴歸零

- [x] 1.1 依 design 決策：D1 匯率 client 與 fallback 表下沉到 Core，把匯率 client 與其傳輸物件自 FX feature 移到 Core 的網路層 (與 HTTP client、設定讀取、錯誤型別同層，因為它是 API client 而非 repository)，把匯率 fallback 表移到 Core 的領域層 (唯一使用者是領域層的匯率快照)。不改任何符號名，所有相依注入的取用點零改動。此為規格 Core and Shared do not reference Feature types 的落地。驗證：FX feature 目錄只剩其 reducer 與 view 兩支檔；iPhone build 成功代表同步群組拾取正確
- [x] 1.2 依 design 決策：D2 測試組裝根移出 Core，把介面測試的五支組裝檔整個目錄自 Core 移到 app 進入點層，與呼叫它的啟動設定同層。此步零改程式碼、零改專案檔。驗證：Core 下不再有測試目錄，五支檔位於 app 進入點層；介面自動化仍可正常啟動並注入替身
- [x] 1.3 [P] 更新上述三類檔案的檔頭註解與文件註解內的路徑描述，以及引用它們的兩支 Core 檔的註解。驗證：內容審視，註解描述的位置與實際位置一致

## 2. 共用元件與語言型別下沉

- [x] 2.1 依 design 決策：D4 共用層元件的三個判準，把選項選擇器移到共用設計系統的選擇器目錄、付款方式編輯器移到共用設計系統的表單目錄。兩者已確認滿足三個判準 (不綁 store、以閉包與呼叫端溝通、不依賴任何 Feature 型別)。依 design 決策：D5 上遷元件不改名，維持原型別名。此為規格 Shared-layer membership has explicit criteria 的落地。驗證：訂單 feature 的元件目錄不再含這兩支檔；13 個呼叫點零改動即編過
- [x] 2.2 在付款方式編輯器的檔頭註明「它是以三個布林旗標參數化的表單，領域語意由呼叫端決定」，避免其存在被讀成「可以把領域元件搬進共用層」的先例。驗證：內容審視
- [x] 2.3 依 design 決策：D3 語言型別整檔下沉，不拆函式，把語言型別連同其本地化方法與導覽標題修飾子整檔移到共用層的本地化目錄，**不**把修飾子單獨拆進共用擴充檔 (只搬函式會讓共用層在函式簽章上依賴 Features 型別，本案的守門測試會立刻抓紅)。驗證：設定 feature 不再含該檔；既有的導覽標題本地化測試不修改即通過

## 3. 分層守門

- [x] 3.1 依 design 決策：D6 分層方向以全樹掃描守門，新增分層守門測試：以自身檔案路徑回推原始碼根目錄，抓出 Features 下**縮排為零**的頂層宣告名，將 Core 與 Shared 下每支檔去除行註解、文件註解與區塊註解後做字界比對，命中即失敗並印出檔名、行號與型別名；找不到原始碼根目錄時記錄失敗而非略過。此為規格 The layering direction is enforced by a source scan 的落地。驗證：該測試在完成任務 1 與 2 後綠
- [x] 3.2 反向驗證守門有效性：刻意把匯率 fallback 表搬回 FX feature，該測試必須失敗並印出正確的檔名與行號；還原後恢復通過。驗證：兩種狀態各跑一次確認，還原後工作樹乾淨
- [x] 3.3 驗證掃描器不誤判：確認 Core 與 Shared 下大量以雙反引號引用 Feature 型別的文件註解不會被判為違例 (這是不去註解就會整片誤紅的主因)。驗證：測試綠即證明去註解生效；另人工抽查三處文件註解引用確認未被列入
