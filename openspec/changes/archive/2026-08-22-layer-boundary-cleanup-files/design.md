## Context

以「列出 Features 下全部頂層宣告名，再回頭掃 Core 與 Shared」的方式全樹重驗後，Core 對 Features 的上行依賴實測為三處 (稽核原記載為一處)：

- 幣別中繼資料 repository 的建構參數型別是 FX feature 的匯率 client
- 領域層的匯率快照在程式碼層直接讀取 FX feature 的匯率 fallback 表
- 介面測試的相依覆寫檔依賴匯率 client、AI client、設定儲存、設定快照與語言型別共五個 Features 型別

其餘命中皆為文件註解內的符號引用 (以雙反引號書寫)，不算真依賴，這也是掃描器必須先去註解的原因，否則會整片誤紅。

跨模組共用但寄居在單一 feature 下的檔案：選項選擇器 609 行、13 個呼叫點遍及設定、報價、匯率、訂單與訂單編輯；付款方式編輯器被主檔管理與選項選擇器共用；語言型別與其導覽標題修飾子住在設定 feature，使用者遍及六個根畫面、設定儲存、根畫面與介面測試組裝。

專案結構前提：整個 app 原始碼資料夾是單一的檔案系統同步群組，搬檔不需改專案檔。

約束：不改任何符號名；不動可及性識別碼與版面；不搬設定儲存 (已被訂單 feature 跨模組依賴)。

## Goals / Non-Goals

**Goals:**

- Core 與 Shared 對 Features 的引用歸零
- 跨模組共用的 UI 元件與語言型別住在共用層
- 上述兩件事由全樹掃描的測試機器守門，而非人工紀律
- 全程零行為變更、零符號改名，可當天驗完並獨立發版

**Non-Goals:**

- 不做 store 邊界收斂 (另案)
- 不搬設定儲存
- 不拆 build target 做真模組化
- 不把上遷元件改名加前綴
- 不改任何符號名、可及性識別碼或版面

## Decisions

### D1 匯率 client 與 fallback 表下沉到 Core

匯率 client 與其傳輸物件放進 Core 的網路層，而非相依注入層：它與 HTTP client、設定讀取、錯誤型別是同一組東西，是 API client 而不是 repository。匯率 fallback 表放進 Core 的領域層，因為它唯一的使用者就是領域層的匯率快照。

此步不改任何符號名，因此所有相依注入的取用點零改動。

### D2 測試組裝根移出 Core

介面測試的五支檔整個目錄移到 app 進入點層，與呼叫它的啟動設定同層。它唯一的呼叫端就是啟動設定，職責是在啟動時把所有 feature 的相依換成替身，這正是組裝根的定義。它認識所有 feature 是合理的，錯的是它掛在 Core 底下。

替代方案是留在 Core 並在守門測試加白名單。已否決：守門測試一開始就帶著例外，而例外會長大。另一個替代方案是把它依賴的三個 Features 型別也一併下沉到 Core，已否決：其中的設定儲存已被訂單 feature 跨模組依賴，下沉會讓範圍失控。

### D3 語言型別整檔下沉，不拆函式

語言型別連同其本地化方法與導覽標題修飾子整檔下沉到共用層的本地化目錄，不把修飾子單獨拆進共用擴充檔。

只搬修飾子的話，共用層的檔案會在函式簽章上直接依賴設定 feature 的語言型別，等於把要修的病從 Core 移植到 Shared，本案新增的守門測試會立刻抓紅。且專案自訂判準寫著「與特定功能耦合的擴充留在該型別檔」，函式與型別不該拆散。語言型別只 import SwiftUI、無任何 Feature 依賴，本來就不是設定專屬。

### D4 共用層元件的三個判準

兩個上遷的元件都滿足：不綁 store、以閉包與呼叫端溝通、不依賴任何 Feature 型別。三者皆滿足才可進共用層，此判準寫進平台指引。

需要特別記錄的是：付款方式編輯器帶著三個領域旗標進入設計系統，可能誘發後續把更多領域元件塞進共用層。緩解是在該檔檔頭註明「它是以三個布林旗標參數化的表單，領域語意由呼叫端決定」，並讓上述三個判準成為明文門檻。

### D5 上遷元件不改名

不加設計系統的名稱前綴。前綴是既有元件的一致慣例但不是明文規則；改名要動 13 個呼叫點、平台指引三處硬規則敘述、規格與介面測試頁面物件的註解，收益只有目錄內命名整齊。改名的差異與本案的分層目的無關，不宜混入。

### D6 分層方向以全樹掃描守門

以自身檔案路徑回推原始碼根目錄，用正則抓出 Features 下**縮排為零**的頂層宣告名 (這天然排除巢狀的通用名稱，例如編碼鍵、狀態、動作、警示、目的地這類每個 feature 都有的型別)，接著把 Core 與 Shared 下每一支檔去掉行註解、文件註解與區塊註解後做字界比對，命中即失敗並印出檔名、行號與型別名。

去註解是必要的：Core 與 Shared 下有大量文件註解以雙反引號引用 Feature 型別，不去註解會整片誤紅。

找不到原始碼根目錄時直接記錄失敗，不用略過掩蓋，略過會讓守門在路徑變動後靜默失效。

## Implementation Contract

**行為**

- 使用者可見行為零變更：本案只移動檔案位置、不改任何符號名或版面
- 匯率查詢、幣別清單載入、報價試算、選項選擇、付款方式編輯、語言切換與導覽標題的行為皆不變

**介面與資料形狀**

- 移動 (不改內容與符號名)：匯率 client 與其傳輸物件 → Core 網路層；匯率 fallback 表 → Core 領域層；介面測試五支檔 → app 進入點層的測試目錄；選項選擇器 → 共用設計系統的選擇器目錄；付款方式編輯器 → 共用設計系統的表單目錄；語言型別整檔 → 共用層本地化目錄
- 修改內容：僅三個檔的檔頭註解與文件註解內的路徑描述，以及引用它們的兩支 Core 檔的註解
- 新增：分層守門測試，含一條全樹掃描斷言

**失敗模式**

- 掃描器找不到原始碼根目錄時必須記錄為失敗，不得以略過掩蓋
- 掃描器必須先去除行註解、文件註解與區塊註解，否則會把文件註解內的符號引用誤判為依賴
- 搬檔後若同步群組未正確拾取，症狀是 build 失敗而非靜默，因此兩個尺寸類別各 build 一次即為充分驗證

**驗收條件**

- Core 與 Shared 下無任何檔案引用 Features 的頂層宣告名 (由守門測試保證)
- 守門測試的有效性經反向驗證：刻意把匯率 fallback 表搬回 FX feature 可讓它失敗，還原後恢復通過
- FX feature 目錄只剩其 reducer 與 view 兩支檔
- Core 下不再有測試目錄，五支介面測試組裝檔位於 app 進入點層
- 訂單 feature 的元件目錄不再含選項選擇器與付款方式編輯器；設定 feature 不再含語言型別檔
- iPhone 與 iPad 各 build 成功一次 (序列執行，build 前已遞增 build number)，無同步群組拾取失敗
- 主 scheme 全部單元測試綠，且基準圖零重錄
- 介面自動化主回歸在兩個尺寸類別各一輪全綠 (識別碼與版面未動，應零改測試碼)
- 平台指引與 README 的專案結構、路徑描述已同步

**範圍界線**

- 在範圍內：上述六類檔案的位置、守門測試、對應文件與新的分層規格
- 不在範圍內：store 邊界、設定儲存、build target 拆分、元件改名、任何符號名或行為

## Risks / Trade-offs

- [搬檔後同步群組未正確拾取，或索引殘留舊路徑] → 整個 app 原始碼資料夾是單一同步群組，搬檔不需改專案檔；仍照平台規定在兩個尺寸類別各 build 一次 (序列執行，兩者共用建置資料庫不可並行)。build 前先遞增 build number，多平台序列 build 只遞增一次
- [守門測試的正則掃描誤判：文件註解內的符號引用、字串字面值內的同名字串] → 比對前先去掉行註解、文件註解與區塊註解；只取 Features 下縮排為零的頂層宣告名，天然排除各 feature 都有的巢狀通用名稱。實作後刻意製造一次違規驗證會失敗、還原後驗證會通過
- [付款方式編輯器帶著領域詞彙進入設計系統，誘發後續把更多領域元件塞進共用層] → 在平台指引寫死共用層的三個判準 (不綁 store、以閉包溝通、不依賴任何 Feature 型別)，三者皆滿足才可進；並在該檔檔頭註明它是以布林旗標參數化的表單、領域語意由呼叫端決定
- [守門測試立起來後，未來有正當理由的跨層引用會被擋住] → 這正是規則要的行為：失敗訊息指出檔名、行號與型別名，把違例轉成一次明確的歸屬討論，而不是靜默通過

## Migration Plan

不涉及持久化資料。本案不動任何持久化模型、版本化 schema 或遷移計畫，migration floor 與 target 皆維持現狀。

兩條相關的硬規則要特別記錄：一、框架無實體級的原名對應，持久化模型的類別名等同實體名，因此持久層下的任何持久化模型在本案一律不搬、不改名，本案連檔案位置都不動；二、本案搬動的六類檔案皆非持久化模型、不參與 schema 指紋，搬移對既有使用者的資料零影響。

使用者偏好亦不受影響：設定儲存的鍵與設定快照的欄位皆未改動，語言型別的原始值保持不變，既有使用者的語言偏好不會被重置。

部署即一般發版，回退即還原程式碼，無殘留狀態。
