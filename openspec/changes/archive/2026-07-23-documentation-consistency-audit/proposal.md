## Why

前八個 change 各自都有一項文件同步任務，依專案的文件同步鐵則檢視自身 diff。但每一項都只在該 change 的範圍內看，看不到三件跨 change 才會顯現的事。

第一是**既有描述被整條推翻**。平台指引目前把收鍵盤記為「以 window 級點擊手勢實作、靠逐層過濾排除系統選單、不可改成對所有 touch 都收鍵盤」——keyboard-dismissal-native-rewrite 會刪掉整個機制，這段從硬規則變成錯誤指引。同一份文件中另有四處會因元件刪除或行為改變而失效：extension 放置規則以收鍵盤修飾子與其檔案為例、本地化規則以分段控制元件為例、Design System 檔名規則以搜尋欄與金額欄元件為例、底部工具列規則的結尾聲稱該擺位在 iPad 仍安全而 navigation-integrity 正要改掉它。這些失效散落在不同 change 的責任邊界之間，每個 change 的作者都可能認為那不是自己的範圍。

第二是**累積後的結構無人負責**。八個 change 合計會往平台指引新增約十五條規則，每個 change 各自「加一節」是合理的局部決定，但累積結果會讓該檔膨脹成流水帳。專案既有的文件慣例要求以主次層級切分、精簡是減字而分層是結構，這件事只能在全部落地後統一處理。

第三是**既有漂移會被誤認為已核對**。稽核時發現的既有不一致與前八個 change 無關：平台說明文件的專案結構樹未列出鍵盤與媒體兩個既有目錄，相依注入目錄描述為「5 個 Repository」而實際數量已增長。若不明確區分來源，這些會在逐項核對時被當成「已檢查過」而繼續留存。

第四是**程式碼註解會以完全相同的方式失效，而既有的風格閘門抓不到**。專案在每個 change 實作完成後會跑一次註解風格審查，但那只看該 change 的變更檔。一條註解可能位於沒被任何 change 修改的檔案，卻因為別處的變更而失效——這與文件的情況完全對稱，且同樣落在責任邊界之間。

稽核前已確認三個案例，各代表一種不同的失效類型。訂單詳情的自繪標題列註解解釋「因本 view 內部已不再使用 NavigationStack，所以以自繪標題列代替系統 navigation title」——ux-honesty-and-visual-foundation 若採首選路徑改由系統標題列承載，這整段因果推理就不再成立。總覽頁的版面註解宣稱在 iPad 上採 1.4 比 1 的權重配置以對應設計稿，但實作是固定寬度上限、做不出比例，而該項已被明確排除於實作範圍之外——這是註解描述的意圖與實作不符，且實作決定不改，因此應修的是註解。選項選擇器中記錄「alert 在實機驗證會 silently 丟掉 Toggle」的註解，其所記錄的知識本身仍然成立，但在 navigation-integrity 把主檔表單全面改用 sheet 之後，這條踩雷知識的適用範圍已超出單一檔案，可能該被提升為文件層級的硬規則。

## What Changes

### 逐 change 核對文件任務確實執行

- 對前八個 change 逐一比對其文件同步任務所宣告的更新項目與文件實際內容，確認每一項都已落地，而非僅在任務清單上被勾選。

### 修正被推翻與失效的描述

- 收鍵盤的硬規則改寫為四條收起路徑與「不得以全域攔截加排除清單實作」的新規則。
- extension 放置規則、本地化規則、Design System 檔名規則中，以已刪除元件為例的部分改用仍存在的元件。
- 底部工具列規則移除「在 iPad 仍安全」的結尾，改為記錄兩種尺寸皆採頂部擺位。

### 以符號存在性驗證文件正確性

- 掃描文件中提及的型別名、檔名與 API 名，逐一確認其在程式碼中確實存在，使「文件正確」成為可驗證的條件而非主觀判斷。

### 整理累積後的結構

- 將八個 change 新增的規則依主次層級重整，合併語意重疊者，確保新增內容不使平台指引退化為流水帳。

### 稽核程式碼註解與現況的一致性

- 掃描註解中描述機制、因果理由與實作意圖的部分，對照現況確認是否仍成立；失效者改寫為反映實際做法。
- 註解中記錄的踩雷知識若已具普遍性且超出單一檔案的適用範圍，識別並記錄其是否該提升為文件層級的硬規則。
- 生成檔的註解不直接修改；若發現問題，記錄為產生器待修項目。

### 修正稽核時發現的既有漂移

- 專案結構樹補上未列出的既有目錄。
- 相依注入目錄的數量描述改為與現況相符，或改為不綁定數量的描述以免再次漂移。

## Non-Goals

- 不修改任何程式邏輯。本 change 對原始碼檔案的變更僅限註解文字，不改動任何可執行語句。
- 不執行註解的風格合規審查。中文用語、結尾標點、半形括號與空格等風格規範由各 change 實作後的專責風格閘門負責；本 change 只處理註解內容與現況是否矛盾。
- 不直接修改生成檔的註解。生成檔由產生器輸出且磁碟上為唯讀，其註解問題應回到產生器處理，本 change 僅記錄。
- 不重寫平台指引與說明文件的整體架構，僅處理因前八個 change 而失效的內容、累積後的層級結構、以及稽核時一併發現的既有漂移。
- 不補齊文件中所有可能過時的描述。既有漂移的處理限縮於稽核過程中實際發現且修正成本低者，並在任務中逐項列出，不做全文重審。
- 不建立自動化的文件檢查工具或持續整合檢查。符號存在性驗證以稽核當下的一次性掃描進行。
- 不變更跨平台通用規範與平台細節的歸屬原則，該分層原則維持現狀。

## Capabilities

### New Capabilities

- `documentation-currency`: 文件與程式碼現況一致的契約——失效描述的處理、符號存在性、以及變更累積後的結構維護責任。
- `code-comment-currency`: 程式碼註解與現況一致的契約——失效註解的判別與處理、生成檔註解的處理途徑、以及與風格閘門的職責分工。

(none)
