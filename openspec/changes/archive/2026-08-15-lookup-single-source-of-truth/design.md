## Context

四種主檔目前的資料流：主檔管理 feature 的清單是一份、訂單 feature 的四個記憶體副本各一份，兩者靠根 feature 的攔截區與約 300 行 cascade helper 保持同步 (該檔目前 758 行)。訂單編輯內新增主檔的四條路徑各自 append 進訂單 feature 自己的副本，因此可見性只有主檔管理頁到訂單編輯這一個方向。

資料層有三份逐字複製：三種只有名稱欄位的主檔，repository 各 108 行、持久層 actor 各 78 行、持久化記錄各 31 行，合計 652 行 (本次重新量測)。Feature 層早已用一個種類列舉統一分流，資料層沒跟上。

共享狀態機制的可用性已查證：`Sharing` 是架構套件 (TCA) 的傳遞相依，原始碼只需 import 架構套件即可看到其 API (`@_exported import`)，**不需新增第三方套件**；但實作階段發現「不需在 Xcode 新增產品」這句原始查證結論有誤：`Sharing` 的型別若要在原始碼中直接具名使用 (如 `SharedKey`、`InMemoryKey`)，仍必須在 Xcode 把它註冊為連結產品，否則編譯過得了、連結階段才會出現 `Undefined symbols`。本專案對此有既有前例：`Dependencies`／`CasePaths`／`Perception`／`PerceptionCore` 同樣是 TCA 的傳遞相依，也都各自被明確加入 `BuyLedger`／`BuyLedgerTests` 兩個 target 的 `packageProductDependencies` 與 Frameworks 連結階段；`Sharing` 已比照辦理 (詳見下方「阻塞已解除」記錄)。全庫目前對它的使用數為 0，本案是第一次使用。

必須繞開的兩顆地雷：

1. 三個持久化記錄的頂層型別同時被兩個保留的 schema 版本引用。依平台指引，改動頂層型別會破壞舊版指紋、導致遷移失敗。這是少數「不改 schema 卻可能破壞遷移」的情境。
2. 泛型參數上的鍵路徑不保證能被持久化框架轉譯成查詢條件，且失敗會發生在執行期而非編譯期。

前置約束：付款旗標的回溯修正必須先落地，本案不得覆蓋它。

## Goals / Non-Goals

**Goals:**

- 四種主檔在 App 內只有一份真相，任一消費端的新增、改名、刪除在同一次狀態更新內對所有消費端生效
- 訂單編輯內新增的主檔對主檔管理頁立刻可見 (修好目前的單向可見性)
- 新增第五種主檔時，漏補分支是編譯錯誤而非執行期靜默不一致
- 三組只有名稱欄位的主檔資料層收斂成泛型，具體型別退化成薄殼
- 上述全部在不改動 schema、不影響既有使用者資料的前提下完成

**Non-Goals:**

- 不新增第五種主檔
- 不動主檔管理的畫面與種類列舉的既有分流語意
- 不把付款方式納入泛型資料層
- 不讓主檔目錄自帶持久化
- 不併「更多」分頁的四個主檔路由
- 不改變任何使用者可見行為，除了修好單向可見性

## Decisions

### D1 主檔以共享的記憶體儲存作為單一來源

新增一份主檔目錄值型別，由訂單 feature 與主檔管理 feature 以架構套件的共享狀態機制指向同一份記憶體儲存。訂單 feature 的四個記憶體副本改為從該目錄導出的計算屬性，主檔管理 feature 的清單與旗標字典同樣改由目錄導出，根 feature 的七個同步 helper 全數刪除。

替代方案是由根 feature 唯一持有目錄，以雙向變更回呼整份覆寫。已否決：那仍是兩份記憶體，每個 action 都要對整份目錄做相等比較，且循環終止依賴「賦相同值不再觸發」這個需要人工推理的性質。共享儲存是唯一真正做到單一儲存的。

代價要講清楚：測試對共享狀態的斷言寫法與既有不同，主檔管理與根 feature 兩組測試的改寫量會增加約三成；且這是專案第一次使用該機制，等於為往後的跨 feature 狀態共享定調。

### D2 目錄不自帶持久化，SwiftData 仍是唯一持久來源

共享儲存採記憶體形式，維持現行「啟動時由 repository 讀取一次」的載入語意。

替代方案是讓目錄自帶檔案持久化、啟動即有值。已否決：專案硬規則是資料唯一來源為 SwiftData 與其共用容器；目錄若自帶持久化，同一份主檔會有資料庫表與檔案兩處真相，等於用新的雙來源換掉舊的多份副本，與本案目標背道而馳。

### D3 差異掛回種類列舉，讓漏補成為編譯錯誤

在種類列舉新增「訂單是否引用此主檔值」與「更名後的訂單」兩個成員，四個分支各自處理訂單來源 (等值)、商品類別 (陣列逐元素)、付款方式 (等值)、對帳狀態 (等值)。根 feature 對訂單表的四段分支判斷收成一段不含分支的映射，唯一的分支收在列舉內受窮舉檢查保護。

同時把訂單重建的 helper 上移為領域型別的手寫擴充 (生成檔不動)，讓它不再是根 feature 的私有實作。

這一步才是本案的核心價值：消除副本只是手段，讓「漏補」從執行期症狀變成編譯期錯誤才是目的。

### D4 四個具名主檔狀態併成以種類為識別的陣列

根 feature 的四個具名主檔狀態併成單一識別陣列，四個 scope 換成一個逐元素的組合，攔截區從十餘個分支降到四個 (付款方式的編輯確認因旗標權威覆寫語意不同而保留為獨立分支)。

不改的話，新增第五種主檔仍要在狀態、action、reducer 三處手動同步，編譯器不會提醒；改了之後這三處變成初始化陣列的一行。

代價是畫面端的四個 scope 要改成可選解包。理論上該陣列以四個種類為固定初值、無任何移除路徑，解包永不失敗，但解包失敗時畫面會靜默空白而非崩潰，因此可選解包的失敗分支要接既有的載入失敗視圖，不可用空視圖。若可選解包讓畫面端過於彆扭，退場方案是保留四個具名狀態、只把攔截收斂成單一處理函式，仍能降到四個分支。

### D5 資料層泛型化不得碰持久化記錄的型別主體

三個持久化記錄的協定遵循一律以擴充補在檔尾，型別主體零差異。硬性禁止在型別主體內新增、移動或改變任何儲存屬性，也不得改類別名 (框架無實體級的原名對應，改名等同新實體)。

理由是這三個頂層型別同時被兩個保留的 schema 版本引用，任何影響屬性指紋的改動都會讓遷移失敗；而遷移失敗在目前的容器建構下會表現為「資料無故清空」而非明確錯誤，症狀與原因距離很遠。

守門方式：既有的兩條落地 store 遷移測試在**不修改測試檔**的前提下必須通過。一旦需要改動該測試檔，就代表本條已被違反，退回重做。

### D6 泛型層不寫查詢條件，由各具體記錄展開

協定要求各具體記錄提供「以名稱比對」的查詢條件靜態方法，由各型別以自身型別展開；泛型層只負責組裝取用描述子，不自行撰寫查詢條件。

理由是泛型參數上的鍵路徑不保證能被持久化框架轉譯，且失敗發生在執行期。這條路徑的直接驗證是泛型持久層測試中的去重與更名合併兩項：若查詢條件沒生效，去重會失敗、更名會產生重複列，測試立刻失敗。

泛型 actor 若因巨集對泛型展開失敗而編不過，退場方案依序為：手寫協定遵循 (巨集展開的內容本來就只有三個成員)；再失敗則保留三個具體 actor、只把四個方法主體抽成泛型自由函式，三個 actor 各剩約 20 行轉呼，仍可消掉約 150 行。實際採用哪一種必須記錄在本 change 內。

### D7 付款方式不納入泛型資料層

付款方式帶三個旗標，其寫入語意是「已存在則更新旗標」、更名要做「任一邊為真就保留」的合併，與只有名稱的主檔的「已存在即無操作」「刪舊列插新列」不同。

為了多消約 100 行而讓泛型層帶上額外的關聯型別與旗標合併策略，會讓泛型層比它取代的重複碼更難讀，也放大巨集展開的風險。三個只有名稱的主檔已佔 652 行的全部，收益已經拿到。

## Implementation Contract

**行為**

- 在主檔管理頁改名任一主檔，主檔管理清單、訂單編輯的可選項清單、以及訂單列表中引用該值的訂單，三者在同一次狀態更新後即同步，不需要額外的 action 往返
- 在訂單編輯 sheet 內新增一個主檔項目後，不重啟 App 直接進入該主檔的管理頁即可看到它 (目前只有反向可見)
- 刪除主檔項目後，訂單編輯的可選項清單不再出現該值
- 付款方式的旗標權威覆寫與其回溯修正行為不變
- 主檔的新增、改名、刪除在兩個尺寸類別上的操作與驗證均不變
- 使用者可見行為除上述可見性缺陷修好之外全部不變

**介面與資料形狀**

- 新增：只有名稱欄位主檔的共用協定 (要求名稱屬性、以名稱建構、以及以名稱比對的查詢條件靜態方法)；泛型持久層 actor (取全部、寫入、刪除、更名四個方法)；操作工廠 (承載去空白與早退語意)；主檔目錄值型別 (四種主檔各一個集合，並提供以種類參數化的讀寫與新增、移除、更名方法)
- 修改：三個持久化記錄僅在檔尾新增協定遵循擴充，型別主體零差異；三個 repository 的對外欄位名、相依鍵與三個注入入口全部保留，僅內部改為綁定到操作工廠；種類列舉新增兩個成員；根 feature 的四個具名主檔狀態併成識別陣列；訂單 feature 的四個記憶體副本改為導出屬性
- 移除：三個具體持久層 actor 檔；根 feature 的七個同步 helper

**失敗模式**

- 泛型 actor 若無法以巨集展開，依 D6 的順序退場，並在本 change 內記錄實際採用哪一種
- 畫面端可選解包失敗時必須顯示既有的載入失敗視圖，不得顯示空視圖 (否則主檔管理頁會靜默空白)
- 若持久化記錄型別主體被改動，遷移會失敗且症狀是資料清空而非明確錯誤；以既有遷移測試不修改即通過作為守門

**驗收條件**

- 根 feature 的七個同步 helper 在全庫零命中，且該檔行數自 758 降到 420 以下
- 三個具體持久層 actor 檔不存在於工作樹；三個 repository 各不超過 55 行；三組資料層 (repository 加持久層加記錄) 合計自 652 行降到 260 行以下
- 三個持久化記錄的差異全部落在新增的擴充內，型別主體零差異 (以逐檔比對確認)
- 訂單 feature 不再有四個主檔記憶體副本的儲存屬性
- 一次性驗證：在種類列舉暫時加入第五個分支後 build，實測分支面涉及 4 支檔共 23 處編譯錯誤 (`LookupKind` 12、`LookupCatalog` 4、`LookupManagementFeature` 5、`LookupManagementView` 2)，根 feature 與訂單 feature 全程零錯誤；記錄結果後還原，此驗證不進入提交 (詳見下方「Task 3.2 一次性驗證結果」)
- 單一測試容器內對任一種類送出更名，主檔管理清單、訂單 feature 的可選項清單、以及訂單列表中引用該值的訂單，三者在同一次 reducer 呼叫後即同步 (不需再送任何 action)
- 訂單編輯內新增主檔後，主檔目錄立即含該項目 (以測試斷言，並於模擬器或實機人工確認一次)
- 既有的兩條落地 store 遷移測試在不修改測試檔的前提下通過
- 付款旗標的既有回溯測試與權威覆寫測試，其斷言不放寬即通過
- 全部單元測試綠 (以重構前的測試數為下限)，iPhone 與 iPad 各 build 成功，介面自動化中主檔管理與訂單編輯相關流程綠
- 平台指引中「cascade 由根 feature 攔截三種 action 處理，新增主檔型別時這兩處都要顧」的敘述已改寫，不再與程式碼矛盾

**範圍界線**

- 在範圍內：四種主檔的單一來源、可見性修復、種類列舉的差異承載、根 feature 攔截區收斂、三個只有名稱主檔的資料層泛型化、對應測試與文件
- 不在範圍內：第五種主檔、主檔管理畫面、付款方式的資料層、目錄的持久化、「更多」分頁路由、訂單 feature 的拆分、任何其他使用者可見行為

## Risks / Trade-offs

- [為了泛型化而改動持久化記錄的型別主體，破壞舊版指紋導致遷移失敗] → 協定遵循一律以檔尾擴充補上，硬性禁止在型別主體內新增、移動或改型別任何儲存屬性；提交前逐檔比對確認型別主體零差異；既有兩條遷移測試不修改即須通過，一旦要改該測試檔就代表已違規，退回重做
- [巨集對泛型 actor 展開失敗，或嚴格並行檢查下隔離不合] → 開工前先寫一個十行的最小驗證確認能否編過；失敗則依 D6 的順序退場，三種結果都在本 change 內記錄實際採用哪一種
- [查詢條件在泛型參數上無法被轉譯，造成執行期回錯結果而編譯期看不出來] → 泛型層完全不寫查詢條件，改由各具體記錄以自身型別展開；泛型持久層測試的去重與更名合併兩項是這條路徑的直接驗證
- [改寫既有主檔與根 feature 測試時，斷言在遷移中被靜默弱化] → 改寫前先把兩組測試的全部斷言抄成清單，改寫後逐條比對；硬性規定不得在這批測試中新增任何原本沒有的關閉窮舉設定；新增的同步斷言一律驗消費端的可選項清單，不只驗目錄本身，避免測到中介狀態而非實際可見行為
- [主檔改名後，可選項清單因合併「訂單裡用過的值」而讓舊名短暫復活] → 可選項清單是目錄與訂單內用過字串的聯集，因此目錄的改名與訂單列表的 cascade 必須在同一次 reducer 呼叫內完成，不可拆成兩個 action 或延到 effect 回呼；以「更名後可選項清單不含舊名」這條斷言鎖住
- [與付款旗標回溯修正的順序倒置，重構覆蓋掉該修正] → 開工第一件事先確認該 change 已封存；若尚未落地，本案不得改動付款方式編輯確認的旗標語意與回溯路徑 (只做 action 形狀與狀態讀取路徑的機械式改寫)，並標註待其落地後回頭合併
- [畫面端改用可選解包後，主檔管理頁在側邊欄或深連結情境下靜默空白] → 可選解包的失敗分支接既有載入失敗視圖而非空視圖；並在兩個尺寸類別各跑一次介面自動化的主檔管理流程，確認四個入口都進得去
- [這是專案第一次使用共享狀態機制，等於為往後的跨 feature 狀態共享定調] → 使用範圍嚴格限制在主檔目錄一處，不順手擴及其他跨 feature 狀態；平台指引中補上使用邊界，避免下次被當成通用作法濫用

## Migration Plan

不涉及 schema 版本升級：schema 檔與遷移計畫一行不動，floor 與 target 皆維持現狀，既有使用者資料零搬遷。

但本案是少數「不改 schema 卻可能破壞遷移」的情境，必須明確約束 (見 D5)：三個持久化記錄的頂層型別同時被兩個保留版本引用，泛型化過程中不得對它們做任何影響屬性指紋的改動：不得改類別名、不得增刪儲存屬性、不得改既有屬性的型別或可選性、不得為了滿足協定而在主體內加欄位。協定遵循、查詢條件靜態方法與任何計算屬性一律寫在擴充，這些不進入框架的屬性集合，安全。付款方式的記錄本次不動。

驗證方式：既有的兩條落地 store 遷移測試 (一條覆蓋跨版本遷移、一條覆蓋目標版直開不觸發階段) 在不修改測試檔的前提下必須通過。此外，因為指紋被破壞時的症狀是資料清空而非明確錯誤，驗收時另需以一台已有資料的實機或已寫入資料的模擬器實開一次 App，確認主檔與訂單都還在。

實施順序：先確認付款旗標回溯修正已落地；再做資料層半場 (可單獨 build 綠、測試綠)；再做狀態層半場。回退即還原程式碼，無殘留狀態。

## ✅ 阻塞已解除 (2026-08-01)：D1 共享狀態機制的連結問題

**問題**：Context 一節原寫「共享狀態機制的可用性已查證……不需在 Xcode 新增產品」。實作階段發現這句話**部分錯誤**：`Sharing` (backing `@Shared` 的套件) 確實是 TCA 的傳遞相依、不需新增第三方套件，但**必須在 Xcode 把它註冊為連結產品**才能在原始碼中直接具名使用其型別 (`SharedKey`、`InMemoryKey` 等)；單純透過 `import ComposableArchitecture` 的 API 表層曝光不足以讓連結器找到 `Sharing` 的符號。

**實測過程**：在 `Features/Lookups/LookupCatalog.swift` 寫入 `extension SharedKey where Self == InMemoryKey<LookupCatalog>.Default { static var lookupCatalog: Self { ... } }` (標準 TCA `@Shared(.inMemory(...))` 具名鍵慣用寫法)，於 iPhone 模擬器建置時連結階段出現 `Undefined symbols ... Sharing.InMemoryKey`／`Sharing.SharedReaderKey`／`Sharing.InMemoryStorage` 等錯誤；以 `xcodebuildmcp utilities clean --scheme BuyLedger` 完整清除後重試兩次，錯誤逐字重現。此錯誤與已知的 `AlertState`／`SwiftNavigation` undefined symbol flaky 連結問題症狀不同：那類 flaky 涉及的符號集固定為 `AlertState`／`SwiftNavigation`、clean 後重跑即消失，本次的符號集是 `Sharing.InMemoryKey`／`Sharing.SharedReaderKey`／`Sharing.InMemoryStorage`、clean 後仍逐字重現。已排除磁碟空間與環境雜訊等干擾因素。

**根因**：`ComposableArchitecture` 的多個傳遞相依 (`Dependencies`、`CasePaths`、`Perception`、`PerceptionCore`) 在本專案 pbxproj 中早已個別以 `XCSwiftPackageProductDependency` 註冊並掛進 `BuyLedger`／`BuyLedgerTests` 兩個 target 的連結階段，`Sharing` 當時尚未比照辦理。這是本專案既有、可驗證的通則：**傳遞相依若要在原始碼中直接具名引用其型別，仍須以 Xcode 手動把該產品加入 target 的連結清單，「傳遞相依」本身不足以讓連結器找到其符號。** 此通則已寫入 `apps/ios/CLAUDE.md` (見「Firebase」節旁新增條目)。

**解除方式**：已由使用者以 Xcode 把 `Sharing` 加入 `BuyLedger` 與 `BuyLedgerTests` 兩個 target (`PBXBuildFile` `D0D98C7D…`／`D0D98C7F…`、Frameworks 連結階段 `:108`／`:120`、`packageProductDependencies` `:208`／`:239`)，操作方式與既有的 `Dependencies`／`CasePaths`／`Perception`／`PerceptionCore` 一致。`LookupCatalog.swift` 的 `SharedKey` 擴充已取消註解並確認可建置，D1 機制原樣採用，未修訂。

## Task 3.2 一次性驗證結果 (2026-08-01 更正)

**問題**：先前記載「加第五個 `LookupKind` 分支後編譯錯誤只出現在種類列舉自身與主檔目錄兩支檔」，此結論不完整：第一輪 build 確實只回報 2 支檔的錯誤，但那是 Swift **批次編譯提早中止**所致，另外兩支排在下一批次的檔案根本沒被編到，並非真的零錯誤。

**實測結果**：把 5 個分支涉及的檔案補齊後重新 build 直到 build succeeded，完整錯誤面為 **4 支檔共 23 處**：`LookupKind.swift` 12 處 (10 個顯示文案 switch 加 `isReferenced(by:name:)`／`renamingReference(in:from:to:)` 兩個 cascade 方法)、`LookupCatalog.swift` 4 處、`LookupManagementFeature.swift` 5 處、`LookupManagementView.swift` 2 處。

**核心宣稱仍成立**：`RootFeature` 與 `OrdersFeature` 全程零錯誤，分支面確實收斂到 `LookupKind` 的兩個 cascade 方法；只是「分支面」本身涉及的檔案數比先前記載的多，這是兩件事，不可混為一談。

**方法論教訓**：驗證編譯期義務的覆蓋範圍時，僅憑首輪批次編譯結果判斷「哪些檔案有錯」不可靠；批次編譯中止後未編到的檔案會被誤判為零錯誤。須反覆「補完已知錯誤所在檔案後再建」直到 build succeeded，才能確定完整錯誤面。
