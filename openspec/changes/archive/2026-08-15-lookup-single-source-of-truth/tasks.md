## 4. 根 feature 攔截區收斂

- [x] 4.2 讓畫面端的四個 scope 改為可選解包，且**失敗分支接既有的載入失敗視圖、不得用空視圖**。此為規格 Lookup item management operations are preserved across platforms 中「無法解析時顯示載入失敗而非空白」的落地。驗證：於 iPhone 與 iPad 各跑一次介面自動化的主檔管理流程，確認四個入口都進得去且畫面正常

## 5. 消除副本，落地單一來源

- [x] 5.1 依 design 決策：D1 主檔以共享的記憶體儲存作為單一來源，新增主檔目錄值型別 (四種主檔各一個集合，並提供以種類參數化的讀寫與新增、移除、更名方法)，放在主檔功能目錄下、不入跨平台生成領域。依 design 決策：D2 目錄不自帶持久化，SwiftData 仍是唯一持久來源，共享儲存採記憶體形式，維持啟動時由 repository 讀取一次的載入語意。驗證：專案可編譯，且目錄的參數化方法有對應單元測試涵蓋四種種類
- [x] 5.2 讓訂單 feature 與主檔管理 feature 以共享狀態機制指向同一份目錄儲存：訂單 feature 的四個主檔記憶體副本改為自目錄導出的計算屬性，主檔管理 feature 的清單與旗標字典同樣改由目錄導出，並刪除根 feature 的七個同步 helper。此為規格 Lookup data has a single source shared by every consumer 的落地。驗證：七個 helper 在全庫零命中、根 feature 行數自 758 降到 420 以下、訂單 feature 不再有四個主檔記憶體副本的儲存屬性
- [x] 5.3 把訂單編輯內新增主檔的四條路徑改為統一寫入同一份目錄，修好目前只有單向的可見性；主檔管理 feature 對清單與旗標字典的直接變更同樣改走目錄的參數化方法，資料庫寫入的 effect 維持不變 (刪除路徑「先寫後改」的既有語意保留)。驗證：新測試 `addingCategoryInsideOrderEditIsVisibleToLookupManagement` 綠，並於模擬器或實機人工確認一次：訂單編輯內新增類別後不重啟 App 直接進類別管理頁即可看到
- [x] 5.4 確認目錄的改名與訂單列表的 cascade 落在**同一個 reducer 分支內**，不拆成兩個 action、不延到 effect 回呼。理由：可選項清單是目錄與訂單內用過字串的聯集，兩者不同步會讓舊名短暫復活。驗證：新測試斷言更名後可選項清單不含舊名

## 6. 測試

- [x] 6.1 改寫根 feature 測試的 action 形狀 (斷言內容不變)，並新增對四種種類各跑一次的同步測試：單一測試容器內送出更名後，主檔管理清單、訂單 feature 的可選項清單、以及訂單列表中引用該值的訂單，三者在同一次 reducer 呼叫後即同步。另新增刪除後訂單編輯不再提供該值的測試。驗證：兩條新測試綠，且改寫後的既有測試斷言逐條比對無遺漏
- [x] 6.2 主檔管理 feature 的既有測試僅調整狀態讀取路徑，**不得放寬斷言、不得新增任何原本沒有的關閉窮舉設定**；另新增「只掛主檔管理 feature 的測試容器上，新增後目錄即含該項目」的測試。驗證：改寫前先把全部斷言抄成清單，改寫後逐條比對；該檔關閉窮舉設定的命中數不高於改寫前。實測改寫涵蓋 17 條既有測試 + 5 條新增測試 (`LookupManagementFeatureTests` 由 17 條增至 22 條)。其中 3 條 (`editConfirmedRenamesPaymentMethodAndClearsFlag`／`editConfirmedKeepsNameAndUpdatesFlags`／`editWithUnchangedFlagsRenamesWithoutRetroactiveConfirmation`) 移除了 `await store.finish()`、改以完整窮舉 `receive` 逐一收乾 effect 鏈，覆蓋淨增是好事；但 `finish()` 另有等待 in-flight effect 的寬限期，若這 3 條日後出現 flaky，成因在此，非邏輯迴歸
- [x] 6.3 [P] 確認付款方式相關測試作為未波及的回歸證明：付款方式持久層測試不修改即通過 (未納入泛型層)，付款旗標的權威覆寫測試與其回溯測試斷言不放寬即通過。此為 design 決策：D7 付款方式不納入泛型資料層 的驗證。驗證：三組測試全綠且無斷言變更
