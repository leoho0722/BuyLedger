## Context

repo 根目錄沒有自動化設定目錄，git hook 目錄只有系統範本，`.claude/settings.json` 也未設任何 hook。跨平台 data model 的漂移檢查是 package 內的手動 script；生成檔的唯讀鎖只作用於本機工作副本。generator 測試目前只對 fixtures 目錄執行漂移檢查，對產線輸出目錄僅做「連續兩次產生結果相同」的決定性驗證，完全不讀磁碟上的生成檔。

iOS 端，主 scheme 的 test action 設為自動建立測試計畫，語言與地區跟隨模擬器；兩份 UI 測試計畫已鎖語言與地區，但都沒有覆蓋率設定。

三個既有約束會直接影響 CI 設計：

- 單元測試以 App 為測試宿主，宿主啟動時會設定 Firebase，而 Firebase 設定檔與 API 金鑰設定檔都被版本庫忽略，乾淨 clone 缺這兩份檔會讓宿主啟動即崩。
- 平台鐵則禁止退回原生 Xcode 命令列工具，一律使用專案指定的建置 CLI。
- 已知踩雷：該 CLI 的測試子命令不理會透過額外參數傳入的測試計畫旗標，篩選必須改用僅測試與略過測試旗標；模擬器名稱會隨 Xcode 升級變動，必須先查詢再以識別碼指定。

repo 為公開專案，因此 macOS runner 不計費。

## Goals / Non-Goals

**Goals:**

- 讓 schema 與生成檔的漂移在推送當下就變紅，而不是等人想起來執行檢查。
- 讓產線輸出目錄本身成為測試的斷言對象。
- 讓單元測試的語言與地區由測試計畫決定，而非模擬器當下狀態。
- 讓覆蓋率成為可查詢的客觀資料。
- 讓乾淨 clone 在沒有任何機密的情況下也能在 CI 完成建置與測試。

**Non-Goals:**

- 不設覆蓋率門檻，也不做覆蓋率趨勢比較。
- 不把 UI 測試納入自動觸發（需模擬器、回歸時間長）。
- 不引入 GitHub secret 或任何機密管理機制。
- 不建立本機 git hook。
- 不改動任何 App production 程式碼、SwiftData schema 或生成結果。
- 不調整既有 UI 測試計畫的略過與選取測試清單。

## Decisions

### 守門放在遠端 CI，不做本機 git hook

本機 hook 有三個致命弱點：可用略過驗證旗標一鍵繞過、換機或重新 clone 後需手動重設 hook 路徑、失敗紀錄不會留在遠端供事後追溯。三者都讓它達不到「機器強制」。維護兩套等價腳本對單人專案是淨負擔。

代價是回饋延遲：要推上去才知道紅。對單人專案而言可接受，因為 codegen job 是秒級的。

### 以入庫的設定範本檔補齊被忽略的機密設定

單元測試以 App 為宿主，宿主啟動會設定 Firebase；建置流程也把 Firebase 設定檔列為輸入。乾淨 clone 缺檔會讓整組測試在 CI 全紅。

作法是比照既有 API 金鑰設定範本的慣例，新增一份 Firebase 設定範本，CI 在建置前複製成正式檔名。值一律為明顯的佔位字串，不含任何真實識別碼。

替代方案：把真檔以編碼形式存成 secret，等於把金鑰交給 CI 平台，而金鑰暴露本來就是本輪待修的風險之一，不採用。另一替代是改啟動流程在偵測不到設定檔時跳過 Firebase 設定，但那會動到 production 啟動路徑，且與後續「遙測 SDK 去留」的決策耦合，不宜在守門案裡先行改動。

範本檔必須加入建置設定的成員例外清單，否則會被檔案系統同步群組自動打包進 App。

### CI 內一律使用專案指定的建置 CLI，不退回原生工具

平台鐵則已禁止退回原生工具，CI 沒有理由破例。workflow 內以釘選版本安裝該 CLI，確保結果可重現，避免上游改參數或輸出格式時無預警把 CI 打紅。

模擬器不寫死名稱：先查詢可用模擬器清單取得識別碼再傳入。找不到符合的執行環境時必須明確失敗，不得退回舊版執行環境讓測試在未支援環境上假綠。

測試篩選使用僅測試與略過測試旗標，不使用測試計畫旗標（已知該 CLI 不理會後者）。

### 分兩段建立信任：codegen job 先成為必過關卡

CI 第一天就整片紅會讓守門從一開始就被當成噪音忽略，那比沒有 CI 更糟。

codegen job 在 Linux runner 上執行，秒級、零外部相依、結果可預期，先讓它成為必過關卡。iOS 單元測試 job 不確定性高（runner 的 Xcode 與執行環境版本、套件解析、snapshot 對外觀與字體敏感），首波排除 snapshot 測試與效能測試，並在失敗時上傳測試結果套件讓失敗可診斷，而不是只看到建置失敗字樣。

snapshot 已知有兩類 false-fail：模擬器外觀入夜自動轉深色會讓淺色 baseline 整批失敗，以及重置模擬器後系統語系改變日期膠囊格式。連續穩定後再把它們收回 CI。

### 主 scheme 改掛測試計畫並鎖定語言與地區

目前主 scheme 設為自動建立測試計畫，語言與地區跟隨模擬器。專案自己已記錄「重置模擬器會改變日期膠囊格式」這個踩雷，而兩張含日期膠囊的 baseline 正好對此敏感，等於已知變因沒有被鎖住。

新增測試計畫並鎖定語言與地區，測試目標維持只掛單元測試 target。保留原有的可測試目標區塊以降低結構落差（既有 UI scheme 也是兩者並存）。

### 覆蓋率只統計 App target，不使用全目標形式

開啟覆蓋率會拉長測試時間並放大測試結果套件體積。因此不使用「全目標」的布林形式，改以物件形式只把 App target 設為統計對象。CI 不設門檻、不做趨勢比較，僅在需要盤點盲區時查詢。

### 產線生成檔納入測試斷言，並鎖住比對標的

目前測試只對 fixtures 執行漂移檢查，產線輸出被手改或漂移時測試仍全綠。新增一條對產線 schema 與設定執行漂移檢查的斷言，失敗訊息必須列出每筆漂移的原因與絕對路徑，並直接寫出修復指令，避免被誤判為 generator 本身壞掉。

同時補一條斷言鎖住產線設定的輸出路徑，否則有人改設定把輸出指向他處，前一條斷言就會失去比對標的而永遠綠燈。

## Implementation Contract

**行為（開發者可觀察）**

- 推送含有「schema 已改但生成檔未重新產生」的 commit 時，遠端 CI 的 codegen job 失敗，失敗步驟為漂移檢查或 generator 測試。
- 推送含有失敗單元測試的 commit 時，iOS 單元測試 job 失敗並附上可下載的測試結果套件。
- UI 測試 job 只在手動觸發時執行；一般推送的執行清單中不出現該 job。
- 本機以主 scheme 執行測試時，語言與地區由測試計畫決定，不再受模擬器系統狀態影響。
- 測試完成後可從測試結果套件查得 App target 的覆蓋率數字。

**介面與資料形狀**

- 新增一份主 scheme 測試計畫，設定語言、地區、執行順序，並以物件形式指定 App target 為唯一覆蓋率統計對象；測試目標為單元測試 target。
- 兩份既有 UI 測試計畫僅新增覆蓋率設定；其餘欄位與略過、選取測試清單維持逐字不變。
- 新增 Firebase 設定範本，含啟動所需的鍵，值為明顯佔位字串，並列入建置設定的成員例外清單。
- CI workflow 觸發條件為推送主分支、拉取請求與手動觸發，並設定同分支取消舊執行。

**失敗模式**

- 找不到符合版本的模擬器執行環境時，job 必須明確失敗，不得退回舊版執行環境。
- 產線生成檔漂移時，測試失敗訊息必須列出每筆漂移的原因與絕對路徑，並附修復指令。
- 缺少設定範本檔導致宿主啟動失敗時，屬於必須在本 change 內解掉的前置，不得以略過測試掩蓋。

**驗收標準**

- 主 scheme 測試計畫存在且可驗其語言、地區與指向 App target 的覆蓋率設定；scheme 中不再出現自動建立測試計畫的設定，改為引用該計畫。
- 兩份 UI 測試計畫的差異只增不改（既有清單逐字不變）。
- 解鎖後手改任一生成檔一個字元，generator 測試出現失敗且訊息含漂移原因與該檔絕對路徑；重新產生後恢復全綠。
- 改動 schema 但不重新產生並推上分支後，codegen job 變紅；還原後轉綠。
- iOS 單元測試 job 在不使用任何 secret 的情況下完成一次綠燈執行，且日誌顯示以識別碼（非寫死名稱）指定模擬器。
- 建置後的 App 產物內不存在設定範本檔；工作樹狀態不出現被忽略的正式設定檔。
- workflow 內對原生 Xcode 命令列工具的搜尋零命中。
- 一般推送的執行清單中不含 UI 測試 job。
- 既有 367 個單元測試在新測試計畫下全綠；UI 主回歸 49 條在補上覆蓋率後仍全綠。

**範圍邊界**

- 在範圍內：CI workflow、三份測試計畫、scheme 的測試計畫掛載、generator 的產線同步斷言、Firebase 設定範本與其 target 排除、相關文件同步。
- 不在範圍內：覆蓋率門檻、UI 測試自動觸發、任何 App production 程式碼、schema 與生成結果、遙測 SDK 的去留、金鑰暴露的修正。

## Risks / Trade-offs

- [CI 首次上線整片紅，守門從第一天就被當成噪音忽略] → 分兩段落地：codegen job 先成為必過關卡；iOS job 先在驗證分支跑到穩定再合入，且首波排除 snapshot 與效能測試，失敗時上傳測試結果套件讓失敗可診斷。
- [runner 鏡像的 Xcode 或模擬器執行環境版本不符，iOS job 根本跑不起來] → 加一個前置步驟印出 runner 的 Xcode 版本與可用模擬器清單，找不到符合版本時明確失敗；若鏡像確實不提供，iOS 測試退回手動觸發，codegen job 仍留在 CI。
- [設定範本檔忘記加入成員例外清單，被打包進 Release 產物] → 驗收明列一條「建置後產物內不存在該檔」的實測；佔位值一律為明顯假字串，即使誤入產物也不會覆蓋或洩漏真實設定。
- [主 scheme 改掛測試計畫後，既有跑法或 Xcode 記憶的選取狀態改變，造成以為跑了其實沒跑] → 保留原有可測試目標區塊以降低結構落差；文件明寫 CLI 端篩選一律使用僅測試與略過測試旗標；以「既有測試全數綠燈」的驗收確認計畫確實掛上且沒有漏跑。
- [generator 測試從此依賴 iOS 端的生成檔，generator 目錄的本機實驗會讓測試紅並被誤判為 generator 壞掉] → 失敗訊息明列每筆漂移的原因與絕對路徑並直接寫出修復指令；跨平台 data model 的說明文件同步說明這條斷言的意圖是守產線輸出，不是 generator 自身回歸。
- [開啟覆蓋率拉長測試時間並放大結果套件體積] → 只把 App target 設為統計對象，不使用全目標形式；不設門檻、不做趨勢比較；結果套件只在失敗時上傳。
- [釘選建置 CLI 版本會讓 CI 停在舊版，錯過上游修正] → 接受此代價以換取可重現性；升級該 CLI 時一併更新 workflow 的釘選版本，並記入平台指引。
